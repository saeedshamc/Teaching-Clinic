# جلسه ۰۱: چرا Go، نصب و ماژول‌ها (۹۰ دقیقه)

**محیط فرض:** Go 1.22 یا جدیدتر · ویندوز / macOS / لینوکس

## پیش‌نیاز
- آشنایی مقدماتی با خط فرمان (ترمینال)
- هیچ دانش قبلی از Go لازم نیست

## اهداف یادگیری
پس از این جلسه می‌توانید:
1. سه دلیل عملی انتخاب Go برای CLI، سرویس و ابزار را توضیح دهید
2. با `go version` و `go env` محیط را بررسی کنید
3. تفاوت **GOPATH** قدیمی با **Module** (ماژول) مدرن را بگویید
4. با `go mod init` یک ماژول بسازید و مسیر `GOMOD` را تفسیر کنید

## چرا این مطلب مهم است
بدون درک ماژول و محیط، هر مثال بعدی یا اجرا نمی‌شود یا وابستگی‌ها اشتباه resolve می‌شوند. تیم‌هایی که هنوز ذهنیت GOPATH دارند، در پروژه‌های واقعی گیج می‌شوند؛ ماژول استاندارد امروز Go است.

## مفهوم اصلی

### Go چیست؟
**Go** (یا Golang) زبانی کامپایل‌شونده با **garbage collector**، سینتکس ساده، و ابزارهای داخلی قوی (`go build`, `go test`, `gofmt`) است. تمرکز طراحی روی خوانایی، سرعت کامپایل، و همزمانی (concurrency) با goroutine است — نه روی ویژگی‌های پیچیدهٔ زبان.

### نصب و تأیید
پس از نصب از [go.dev/dl](https://go.dev/dl/):

```bash
go version
# نمونه خروجی: go version go1.22.5 windows/amd64

go env GOVERSION GOROOT GOPATH GOMOD
```

| متغیر | معنی |
|--------|------|
| `GOROOT` | محل نصب خود Go |
| `GOPATH` | فضای workspace قدیمی / کش ماژول‌ها |
| `GOMOD` | مسیر `go.mod` فعال؛ اگر خارج ماژول باشید خالی یا `/dev/null` است |

### Module به‌جای GOPATH
قدیم‌تر پروژه‌ها باید زیر `GOPATH/src/...` می‌نشستند. امروز:

```bash
mkdir hello-go && cd hello-go
go mod init example.com/hello
```

فایل `go.mod` نام ماژول و نسخهٔ حداقل Go را نگه می‌دارد. همهٔ `import`های خارجی نسبت به همین نام resolve می‌شوند.

## اشتباهات رایج
1. **نصب بدون افزودن به PATH** — ترمینال `go` را پیدا نمی‌کند؛ ترمینال را بعد از نصب باز کنید یا PATH را چک کنید.
2. **ساخت پروژه بدون `go mod init`** — بعداً `go get` و importها گیج‌کننده می‌شوند.
3. **فرض اینکه GOPATH هنوز محل اجباری سورس است** — برای کد جدید لازم نیست؛ Module کافی است.

## مثال آموزشی قدم‌به‌قدم

از ریشهٔ پوشهٔ `Go/` (جایی که `go.mod` دوره هست):

```bash
cd session-01-intro/examples
go run .
```

محتوای `examples/main.go`:

```go
package main

import (
	"fmt"
	"runtime"
)

func main() {
	fmt.Printf("نسخه Go: %s | سیستم: %s/%s\n",
		runtime.Version(), runtime.GOOS, runtime.GOARCH)
}
```

خروجی شبیه: `نسخه Go: go1.22.x | سیستم: windows/amd64`

## نسخهٔ بهتر / الگوی درست
به‌جای کپی‌کردن باینری Go به چند مسیر تصادفی، یک نصب رسمی + یک `PATH` تمیز + همیشه `go mod init` در ریشهٔ پروژه. برای چند پروژه، هر کدام ماژول جدا با نام یکتا (مثلاً `example.com/clinic/session01`).

## تمرین عملی

### آسان
1. `go version` و `go env GOOS GOARCH GOMOD` را اجرا و خروجی را یادداشت کنید.
2. در یک پوشهٔ موقت `go mod init example.com/practice01` بزنید و محتوای `go.mod` را بخوانید.

### چالش
با تنظیم موقت `GOOS` و `GOARCH` (مثلاً `linux`/`amd64`) یک binary کراس‌کامپایل بسازید:

```bash
# PowerShell
$env:GOOS="linux"; $env:GOARCH="amd64"; go build -o hello-linux .
```

سپس متغیرها را به حالت عادی برگردانید و توضیح دهید چرا فایل روی ویندوز مستقیماً اجرا نمی‌شود.

## راهنمای راه‌حل (چالش)
1. داخل `examples` باشید تا پکیج `main` پیدا شود.
2. `GOOS`/`GOARCH` فقط برای همان نشست ترمینال تنظیم شوند.
3. `go build -o نام‌فایل .` خروجی را می‌سازد؛ `go run` برای کراس‌کامپایل هدف نهایی نیست.
4. در پایان `$env:GOOS=$null; $env:GOARCH=$null` (PowerShell) یا بستن ترمینال.
