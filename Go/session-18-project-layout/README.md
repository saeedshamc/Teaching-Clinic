# جلسه ۱۸: ساختار پروژه واقعی — cmd / internal / pkg (۹۰ دقیقه)

**محیط فرض:** Go 1.22+

## پیش‌نیاز
- جلسات ۰۱ تا ۱۷

## اهداف یادگیری
پس از این جلسه می‌توانید:
1. نقش `cmd/`، `internal/` و `pkg/` را توضیح دهید
2. بگویید چرا `internal` از import بیرونی محافظت می‌کند
3. یک اسکلت آموزشی کوچک با این لایه‌ها طراحی کنید
4. از گذاشتن همه چیز در `package main` در پروژه‌های بزرگ‌تر پرهیز کنید

## چرا این مطلب مهم است
بدون قرارداد پوشه، importهای حلقه‌ای و «همه‌چیز export شده» سریع رشد می‌کند. اکوسیستم Go روی این اسکلت به اجماع نسبی رسیده است.

## مفهوم اصلی

| مسیر | نقش |
|------|-----|
| `cmd/app/main.go` | نقطه ورود؛ نازک |
| `internal/...` | کد خصوصی همین ماژول؛ دیگران نمی‌توانند import کنند |
| `pkg/...` | کتابخانهٔ عمداً عمومی (اختیاری؛ خیلی‌ها کمتر استفاده می‌کنند) |

قانون Go: هر مسیر شامل `/internal/` باشد، فقط والد درخت می‌تواند import کند.

## اشتباهات رایج
1. **منطق زیاد داخل main**
2. **export کردن همه چیز از ریشهٔ ماژول بدون نیاز**
3. **ساختن pkg خالی فقط برای مُد روز** — اگر عمومی نیست، internal بهتر است

## مثال آموزشی قدم‌به‌قدم
در این جلسه اسکلت را مفهومی می‌سازیم (بدون اپ غول). نمونهٔ حداقلی در `examples/layout.txt` درخت پیشنهادی را نشان می‌دهد و `examples/main.go` فقط چاپ می‌کند که entrypoint کجاست.

```bash
cd session-18-project-layout/examples
go run .
```

## نسخهٔ بهتر / الگوی درست
شروع با `cmd` + `internal`. وقتی واقعاً کتابخانهٔ جدا برای دیگران دارید، `pkg` یا ماژول جدا.

## تمرین عملی

### آسان
روی کاغذ (یا فایل) درخت یک CLI با `cmd/cli` و `internal/config` بکشید.

### چالش
توضیح دهید چرا یک ریپو بیرونی نمی‌تواند `yours.com/mod/internal/secret` را import کند.

## راهنمای راه‌حل (چالش)
کامپایلر Go import مسیر دارای `internal` را اگر خارج از درخت والد باشد رد می‌کند — این اجبار زبان است نه قرارداد اجتماعی.
