# جلسهٔ ۱۹ — توابع و کلاس‌های friend

> `friend` کلید یدکی است: لازم است، ولی هر کسی نباید داشته باشد.

---

## اهداف این جلسه

1. بدانید `friend` دقیقاً چه اجازه‌ای می‌دهد و چه اجازه‌ای **نمی‌دهد**.
2. تابع `friend` بنویسید و بفهمید چرا `operator<<` گاهی به آن نیاز دارد.
3. کلاس `friend` را بشناسید و یک‌طرفه بودنش را ببینید.
4. هزینه‌های `friend` و جایگزین‌های آن (`getter`، تابع عضو، رابط عمومی) را بسنجید.
5. قاعده‌ای برای تصمیم‌گیری داشته باشید: کِی `friend` و کِی نه.

---

## ۱. `friend` چیست؟

`friend` اجازهٔ دسترسی به اعضای **private** و **protected** یک کلاس را به یک تابع یا کلاس دیگر می‌دهد، بدون اینکه آن اعضا `public` شوند.

```cpp
class Matrix2x2 {
    friend std::ostream& operator<<(std::ostream& out, const Matrix2x2& matrix);
private:
    double a_, b_, c_, d_;
};
```

نکتهٔ مهم: `friend` بخشی از **رابط عمومی** کلاس نیست. کاربر کلاس نمی‌تواند `matrix.a_` بنویسد؛ فقط خود تابع اعلام‌شده می‌تواند.

### چه چیزی `friend` نیست

| تصور غلط | واقعیت |
|---|---|
| «friend یعنی زیرکلاس» | نه؛ زیرکلاس از طریق `protected` دسترسی دارد |
| «friend ارث می‌رسد» | نه؛ زیرکلاسِ friend، friend نیست |
| «friend دوطرفه است» | نه؛ اگر `A` دوست `B` باشد، `B` دوست `A` نیست |
| «friend قابل انتقال است» | نه؛ اگر `A` دوست `B` و `B` دوست `C` باشد، `C` دوست `A` نیست |

---

## ۲. تابع `friend`

```cpp
class Matrix2x2 {
public:
    friend Matrix2x2 add(const Matrix2x2& left, const Matrix2x2& right);
    friend std::ostream& operator<<(std::ostream& out, const Matrix2x2& matrix);
};

Matrix2x2 add(const Matrix2x2& left, const Matrix2x2& right) {
    return Matrix2x2(left.a_ + right.a_, left.b_ + right.b_,
                     left.c_ + right.c_, left.d_ + right.d_);
}
```

سه چیز که باید بدانید:

1. **محل اعلان**: `friend` داخل کلاس نوشته می‌شود، ولی تابع عضو کلاس **نیست**. `matrix.add(other)` ممکن نیست؛ `add(matrix, other)` درست است.
2. **بدون `friend` هم کامپایل می‌شود** اگر تابع را با getter بنویسید. `friend` فقط راه دسترسی مستقیم است، نه لازمهٔ وجود.
3. **تعریف داخل کلاس**: می‌توانید تابع friend را همان‌جا تعریف کنید (inline) — برای `operator<<` کوتاه رایج است.

### چرا `operator<<` اغلب friend است؟

```cpp
std::ostream& operator<<(std::ostream& out, const Money& money) {
    return out << money.cents_;      // نیاز به دسترسی خصوصی
}
```

اگر `toString()` عمومی داشته باشید، friend لازم نیست (همان کاری که در جلسهٔ ۱۸ کردیم). اگر نخواهید برای هر کلاس یک متد چاپ عمومی بسازید، friend گزینهٔ تمیزتری است: چاپ، بخشی از **رابط** کلاس می‌شود بدون آن‌که داده باز شود.

---

## ۳. کلاس `friend`

```cpp
class Engine {
    friend class Doctor;
private:
    int runCount_ = 0;
    int totalSeconds_ = 0;
};

class Doctor {
public:
    void diagnose(const Engine& engine) const {
        std::cout << engine.runCount_ << " بار روشن شده\n";   // ✅
    }
};
```

- کل `Doctor` به **همهٔ** اعضای خصوصی `Engine` دسترسی دارد.
- این دسترسی یک‌طرفه است: `Engine` چیزی از `Doctor` نمی‌بیند.
- هر تغییری در اعضای خصوصی `Engine` می‌تواند `Doctor` را بشکند؛ همین، هزینهٔ اصلی است.

### کِی کلاس friend منطقی است؟

- دو کلاس که **با هم** یک مفهوم را می‌سازند و مرزشان مصنوعی است (مثلاً `Iterator` و `Container`).
- عملگر/کلاس کمکی که بدون دسترسی، فقط با getterهای زیاد کار می‌کند.
- در بقیهٔ موارد، رابط عمومی بهتر است.

در خروجی برنامه، `Mechanic` همان کار را **بدون** friend انجام می‌دهد — با اطلاعات کمتر. این تفاوت مهم است: friend اطلاعات بیشتری می‌دهد، نه امکان بیشتری برای انجام کار.

---

## ۴. هزینه‌های `friend` و جایگزین‌ها

| گزینه | سود | هزینه |
|---|---|---|
| `friend` | دسترسی مستقیم و سریع، بدون getter اضافه | کوپلینگ؛ تغییر داخلی، friend را می‌شکند |
| `getter` عمومی | مرز روشن | رابط بزرگ می‌شود؛ بعضی getterها فقط برای یک مصرف‌کننده‌اند |
| متد عضو عمومی | رفتار در جای درست | برای `operator<<` کار نمی‌کند (شیء چپ استریم است) |
| تابع آزاد + `toString()` | بدون friend، تست‌پذیر | یک متد عمومی اضافه |

**قاعده:** اگر `friend` فقط برای یک تابع کمکی کوچک است و می‌توانید با یک متد عمومی تمیزش کنید، متد عمومی را انتخاب کنید. اگر تعداد getterها از حد گذشت یا getter فقط برای چاپ بود، `friend` بهتر است.

### `friend` و تست

`friend` تست را سخت نمی‌کند، ولی **دسترسی تست به internals** را آسان می‌کند — که خودش یک تله است: تستی که به دادهٔ خصوصی وابسته است، با هر بازطراحی می‌شکند. تست را روی رابط عمومی بنویسید.

## ۶. اشتباهات رایج

1. **`friend` برای دور زدن طراحی بد**: اگر برای هر تابع جدید یک friend اضافه می‌کنید، مرز کلاس اشتباه است.
2. **انتظار دسترسی دوطرفه**: `friend class Doctor;` در `Engine` به `Doctor` اجازه می‌دهد، نه برعکس.
3. **فراموش کردن اعلان در کلاس**: تابع friend باید داخل کلاس اعلان شود، وگرنه همان تابع آزاد معمولی است و به private دسترسی ندارد.
4. **تعریف friend در هدر و ODR**: تعریف inline داخل کلاس امن است؛ تعریف جدا در هدر بدون `inline` باعث خطای لینک می‌شود.
5. **`friend` برای همه‌چیز** → کپسوله‌سازی تشریفاتی می‌شود.
6. **دوست کردن کلاس پایه/مشتق** به انتظار دسترسی متقابل — ارث و friend دو مکانیزم جدا هستند.
7. **`friend` به‌جای getter برای داده‌ای که واقعاً عمومی است** — اگر همه به آن نیاز دارند، شاید باید عمومی باشد.

---

## ۷. بهترین شیوه‌ها

- `friend` را **کوچک و محدود** نگه دارید: یک تابع، نه یک کلاس بزرگ.
- برای `operator<<`/`operator>>` که به داده نیاز دارند، friend گزینهٔ استاندارد است.
- وقتی `toString()` یا getter کافی است، friend را اضافه نکنید.
- `friend` را نزدیک اعضای خصوصی و با توضیح دلیل بنویسید.
- به یاد داشته باشید `friend` بخشی از رابط عمومی است: تغییرش می‌تواند کد دیگران را بشکند.
- هرگز برای دسترسی به اعضای `private` کلاس دیگر، `friend` را به‌عنوان اولین راه انتخاب نکنید.

---

## ۸. خلاصه

- `friend` دسترسی به `private`/`protected` می‌دهد، بدون عمومی کردن آن‌ها.
- یک‌طرفه، غیرقابل ارث‌بری و غیرقابل انتقال است.
- تابع friend، عضو کلاس نیست.
- `operator<<` و `operator>>` رایج‌ترین کاربردهای مشروع آن‌اند.
- هر friend، یک نقطهٔ کوپلینگ جدید است؛ کم نگه دارید.

### تمرین ۱ — `Vector2D` و عملگر friend (متوسط)

`exercises/exercise_01.cpp`: چرا `2.0 * v` باید friend باشد؟

```cpp
double operator*(const Vector2D& other) const;              // v1 * v2 (ضرب داخلی)
friend Vector2D operator*(double factor, const Vector2D& v); // 2.0 * v
friend std::ostream& operator<<(std::ostream& out, const Vector2D& v);
```

```
a = (3, 4) ، |a| = 5
b = (1, 2)
a + b = (4, 6)
a · b = 11
2.5 * a = (7.5, 10)
3 * b = (3, 6)
```

دو نکته:

1. در `2.0 * a` شیء چپ `double` است؛ متد عضو نمی‌تواند این حالت را پوشش دهد. عملگر friend این کار را می‌کند.
2. عملگر member و friend هم‌نام اشکالی ندارند؛ **overloading** بر اساس نوع پارامترهاست. توجه کنید `a * 2.5` کار **نمی‌کند**، چون friend فقط جهت `(double, Vector2D)` را تعریف کرده؛ برای آن جهت دیگر یک overload جدا لازم است.
