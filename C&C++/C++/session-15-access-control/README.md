# جلسهٔ ۱۵ — سطوح دسترسی، getter/setter و اعتبارسنجی

> `private` کردن داده، نصف کار است؛ نصف دیگر این است که راه تغییر را درست طراحی کنید.

---

## اهداف این جلسه

1. سه سطح دسترسی `public`، `private` و `protected` را بشناسید و بدانید کدام کجا به کار می‌آید.
2. getter و setter را **درست** بنویسید: getter بدون کپی، setter با اعتبارسنجی.
3. تفاوت «عضو محاسبه‌شده» و «عضو ذخیره‌شده» را ببینید و از ذخیرهٔ داده‌های تکراری پرهیز کنید.
4. `const` را در رابط کلاس جدی بگیرید: متد `const`، پارامتر `const&`.
5. بدانید چرا بعضی مقادیر **نباید** setter داشته باشند.

---

## ۱. سه سطح دسترسی

| سطح | چه کسی می‌بیند | چه زمانی |
|---|---|---|
| `public` | همه | بخشی از قرارداد کلاس؛ تغییرش کد کاربران را می‌شکند |
| `private` | فقط اعضای همان کلاس | پیاده‌سازی داخلی؛ آزادانه تغییر می‌کند |
| `protected` | کلاس و کلاس‌های مشتق | برای زمانی که زیرکلاس باید به داده دسترسی داشته باشد (جلسهٔ ۲۰) |

تفاوت `private` و `protected` فقط با وراثت معنی پیدا می‌کند. تا جلسهٔ ۲۰، عملاً همان `private` است.

```cpp
class Book {
public:
    double price() const;              // خواندن: آزاد
    bool setPrice(double value);       // نوشتن: کنترل‌شده

private:
    double price_ = 0.0;               // داده: پنهان
};
```

**قاعدهٔ طلایی:** داده‌ها `private`، رفتار `public`. اگر عضوی را `public` گذاشتید، عملاً همان `struct` جلسهٔ ۱۲ را ساخته‌اید.

---

## ۲. getter درست

```cpp
const std::string& title() const { return title_; }   // بدون کپی، فقط‌خواندنی
double price() const { return price_; }               // نوع کوچک، با ارزش
int stock() const { return stock_; }
```

سه نکته:

1. **`const` انتهای متد** واجب است. بدون آن، `printPerson(const Person&)` نمی‌تواند `person.name()` را صدا بزند.
2. برای `std::string` و انواع سنگین، `const&` برگردانید؛ برای `int`/`double` با ارزش.
3. هرگز `std::string&` (بدون `const`) برنگردانید — یعنی کلید داده را به دست کاربر داده‌اید:
   ```cpp
   std::string& title() { return title_; }   // ❌ book.title() = ""؛
   ```

### عضو محاسبه‌شده را ذخیره نکنید

```cpp
double totalValue() const { return price_ * static_cast<double>(stock_); }
bool isAvailable() const { return stock_ > 0; }
```

این‌ها getter نیستند؛ **محاسبه** هستند. اگر `totalValue_` را به‌عنوان عضو ذخیره کنید، باید در هر تغییر قیمت یا موجودی آن را هم به‌روز کنید — و روزی یکی از این به‌روزرسانی‌ها جا می‌افتد. دادهٔ مشتق‌شده را در لحظهٔ نیاز حساب کنید.

---

## ۳. setter درست

```cpp
bool setPrice(double value) {
    if (value < 0.0) {
        return false;          // ۱) بررسی
    }
    price_ = value;            // ۲) نوشتن
    return true;               // ۳) گزارش موفقیت
}
```

ترتیب مهم است. الگوی غلط:

```cpp
void setPrice(double value) {
    price_ = value;
    if (price_ < 0.0) {
        price_ = 0.0;          // ❌ اول خراب کردیم، بعد ترمیم
    }
}
```

در کد دوم، اگر بین این دو خط استثنا یا بازگشتی رخ دهد، شیء خراب می‌ماند. همیشه **اول بررسی، بعد نوشتن**.

### آیا همهٔ اعضا باید setter داشته باشند؟

نه. سه دسته را از هم جدا کنید:

| نوع عضو | مثال | setter؟ |
|---|---|---|
| تغییرناپذیر | `id`، تاریخ تولد | ❌ فقط سازنده |
| تغییرپذیر با قاعده | `price`، `age` | ✅ با اعتبارسنجی |
| مشتق‌شده | `totalValue`، `average` | ❌ محاسبه |

`id` را در جلسهٔ ۱۶ با شمارندهٔ `static` می‌سازیم؛ همان‌جا دوباره می‌بینید که «بدون setter» یک تصمیم طراحی است، نه فراموشی.

---

## ۴. عملیات دامنه‌ای بهتر از setter خام

```cpp
bool sell(int count) {                 // ✅ دامنه را می‌فهمد
    if (count <= 0 || count > stock_) {
        return false;
    }
    stock_ -= count;
    return true;
}
```

در مقابل `setStock(stock_ - count)` که کاربر می‌تواند هر مقدار بی‌معنی‌ای بدهد. عملیات دامنه‌ای:

- نامش منظور را می‌رساند.
- می‌تواند قاعده‌های چندعضوی را حفظ کند (مثلاً «فروش باعث منفی شدن موجودی نشود»).
- در لاگ و تست خواناتر است.

---

## ۵. `const` بخشی از رابط است

```cpp
void printPerson(const Person& person) {
    std::cout << person.name() << " (" << person.age() << ")\n";
}
```

- پارامتر `const&`: بدون کپی و بدون امکان تغییر.
- داخل این تابع فقط متدهای `const` قابل فراخوانی‌اند.
- اگر `age()` را بدون `const` بنویسید، همین تابع کامپایل نمی‌شود — و مجبور می‌شوید کپی بگیرید یا `const` را بردارید؛ هر دو بدترند.

در خروجی `02_validation.cpp`، `reader` یک شیء `const` است و از `printPerson` عبور می‌کند؛ همین که کامپایل می‌شود یعنی رابط کلاس `const`-درست است.

## ۷. اشتباهات رایج

1. **`public` گذاشتن داده** چون «سریع‌تر است» → invariant از دست می‌رود.
2. **getter بدون `const`** → کلاس در کدهای `const` غیرقابل استفاده می‌شود.
3. **برگرداندن `std::string&` غیر const** → کلید داده به کاربر.
4. **setter بدون بررسی** یا **بررسی بعد از نوشتن**.
5. **ذخیرهٔ دادهٔ مشتق‌شده** و فراموش کردن به‌روزرسانی آن.
6. **setter برای شناسه** (`setId`) — شناسه باید در سازنده تعیین و بعد تغییرناپذیر شود.
7. **setter عمومی برای همه‌چیز** → دوباره به `struct` عمومی رسیده‌اید، فقط با کد بیشتر.
8. **انجام اعتبارسنجی در `main`** به‌جای کلاس → هر مسیر ورود جدید، یک باگ جدید.
9. **پیام خطای گنگ**: `false` بدون این‌که معلوم باشد کدام قاعده شکست (در پروژه‌های بزرگ‌تر `enum` خطا یا استثنا).

---

## ۸. بهترین شیوه‌ها

- همهٔ داده `private`؛ فقط رفتار `public`.
- getterها `const`، و برای انواع سنگین `const&`.
- setter: بررسی → نوشتن → `return true`.
- به‌جای setter خام، عملیات دامنه‌ای (`sell`، `withdraw`، `promote`).
- عضو مشتق‌شده را محاسبه کنید، ذخیره نکنید.
- پارامترهای تابع را `const&` بگیرید (به‌جز انواع کوچک).
- اگر عضوی تغییرناپذیر است، setter نداشته باشد و در سازنده تنظیم شود.
- رابط را کوچک نگه دارید: هر متد عمومی، تعهد نگهداری است.

---

## ۹. خلاصه

- `public` قرارداد، `private` پیاده‌سازی، `protected` برای زیرکلاس‌ها.
- getter خوب: `const` و بدون کپی غیرضروری.
- setter خوب: اعتبارسنجی قبل از نوشتن.
- دادهٔ مشتق‌شده محاسبه می‌شود، نه ذخیره.
- `const`-درستی رابط، کلاس را در کد واقعی قابل استفاده می‌کند.
