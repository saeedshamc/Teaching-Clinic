# جلسهٔ ۱۱ — حافظهٔ پویا: `new`، `delete` و دام‌هایش

> این جلسه ابزاری را نشان می‌دهد که C++ را قدرتمند و در همان حال خطرناک می‌کند. هدف: بفهمید چطور کار می‌کند، و بعد یاد بگیرید چرا تقریباً هیچ‌وقت از آن استفاده نکنید.

---

## اهداف این جلسه

1. تفاوت stack و heap را بفهمید.
2. با `new` و `delete` یک شیء بسازید و آزاد کنید.
3. با `new[]` و `delete[]` آرایهٔ با اندازهٔ زمان اجرا بسازید.
4. پنج دام اصلی حافظه را بشناسید: نشتی، dangling pointer، double free، `delete` اشتباه و نشت در مسیر خطا.
5. بدانید چرا `std::vector` جایگزین بهتری است.

---

## ۱. stack و heap

| | stack | heap |
|---|---|---|
| چه چیزی | متغیرهای محلی، پارامترها | حافظهٔ تخصیص‌یافته با `new` |
| اندازه | کوچک (معمولاً ۱ تا ۸ مگابایت) | تا حد زیادی بزرگ |
| سرعت | خیلی سریع | کندتر |
| عمر | تا پایان دامنه | تا `delete` |
| اندازه در زمان اجرا | ❌ | ✅ |
| مدیریت | خودکار | **دستی** |

```cpp
void demo() {
    int local = 5;              // stack: با پایان تابع آزاد می‌شود
    int* onHeap = new int(5);   // heap: تا delete زنده می‌ماند
    delete onHeap;              // اگر این خط نباشد، نشتی داریم
}
```

هزینهٔ heap این است که **شما** مسئول آزادسازی هستید. همین یک جمله منبع تقریباً همهٔ باگ‌های حافظه در C و C++ است.

---

## ۲. `new` و `delete` برای یک شیء

```cpp
int* p = new int(42);    // تخصیص + مقدار اولیه
std::cout << *p;         // 42

*p = 100;                // تغییر مقدار

delete p;                // آزادسازی
p = nullptr;             // جلوگیری از استفادهٔ تصادفی
```

- `new int` (بدون پرانتز): حافظه گرفته می‌شود ولی **مقدار نامعلوم** دارد. چاپش نکنید.
- `new int()` (با پرانتز خالی): مقدار صفر.
- `new int(42)`: مقدار ۴۲.

برای شیء کلاسی، `new` **سازنده** را صدا می‌زند و `delete` **مخرب** را (جلسهٔ ۱۴):

```cpp
std::string* text = new std::string("heap");
text->append(" allocation");        // دسترسی به عضو با ->
delete text;
```

`p->member` همان `(*p).member` است.

---

## ۳. `new[]` و `delete[]` برای آرایه

آرایهٔ خام اندازهٔ ثابت زمان کامپایل دارد. با `new[]` اندازه در زمان اجرا تعیین می‌شود:

```cpp
int n = 0;
std::cin >> n;

int* data = new int[n];     // n عنصر
for (int i = 0; i < n; ++i) {
    std::cin >> data[i];
}

delete[] data;              // حتماً با براکت!
data = nullptr;
```

**قاعدهٔ سخت‌گیرانه:**

| تخصیص | آزادسازی |
|---|---|
| `new T` | `delete p` |
| `new T[n]` | `delete[] p` |

اشتباه کردن این دو **رفتار تعریف‌نشده** است و اغلب باعث خرابی heap می‌شود — گاهی همان لحظه، گاهی صد خط بعد.

> `new[]` ابتدا تعداد عناصر را ذخیره می‌کند تا `delete[]` بداند چند مخرب را صدا بزند؛ به همین دلیل `delete` ساده با آن سازگار نیست.

---

## ۴. پنج دام حافظه

### دام ۱: نشتی (memory leak)

```cpp
void leaky() {
    int* data = new int[100];
    // ... استفاده ...
}   // بدون delete[] → این حافظه تا پایان برنامه گم می‌شود
```

در برنامهٔ کوتاه شاید دیده نشود؛ در سرور ۲۴ ساعته، حافظه مدام بالا می‌رود تا crash.

### دام ۲: اشاره‌گر آویزان (dangling pointer)

```cpp
int* p = new int(7);
delete p;
std::cout << *p;    // ❌ حافظه آزاد شده؛ مقدار ممکن است هنوز همان ۷ باشد!
```

این بدترین نوع باگ است: **ممکن است کار کند**. بعد از `delete` همیشه `p = nullptr;` بگذارید تا اگر جایی اشتباهاً استفاده شد، حداقل crash قطعی بگیرید نه خرابی خاموش.

### دام ۳: آزادسازی دوباره (double free)

```cpp
int* p = new int(1);
delete p;
delete p;    // ❌ دو بار آزادسازی همان بلوک
```

### دام ۴: `delete` به‌جای `delete[]`

```cpp
int* arr = new int[10];
delete arr;    // ❌ باید delete[] باشد
```

### دام ۵: نشت در مسیر خطا

```cpp
int* data = new int[10];
if (somethingFailed) {
    return;         // ❌ delete[] اجرا نمی‌شود
}
```

هر `return` یا `throw` یا `break` زودهنگام می‌تواند آزادسازی را دور بزند. راه‌حل ساختاری: **RAII** — مالکیت را در یک شیء بگذارید تا مخربش آزاد کند (جلسهٔ ۳۸). `std::vector` و `std::string` دقیقاً همین کار را می‌کنند.

---

## ۵. جایگزین مدرن

```cpp
// قبل
int* numbers = new int[n];
for (int i = 0; i < n; ++i) {
    numbers[i] = 0;
}
// ... استفاده ...
delete[] numbers;

// بعد
std::vector<int> numbers(static_cast<std::size_t>(n), 0);
// ... استفاده ...
// هیچ delete‌ای لازم نیست
```

`std::vector`:
- اندازه را می‌داند،
- خودش بزرگ می‌شود،
- با استثنا و `return` زودهنگام هم درست آزاد می‌شود،
- با `at()` مرز را بررسی می‌کند.

در C++ مدرن `new` خام فقط در کد سطح پایین (ساخت کانتینر، پلاگین، API زبان C) دیده می‌شود. برای مالکیت منفرد، `std::unique_ptr` (جلسهٔ ۳۶) جای `new`/`delete` را می‌گیرد.

## ۷. اشتباهات رایج

1. **فراموش کردن `delete`** → نشتی.
2. **`delete` به‌جای `delete[]`** → رفتار تعریف‌نشده.
3. **دو بار `delete`** → خرابی heap.
4. **استفاده بعد از `delete`** → مقدار قدیمی یا crash.
5. **دسترسی به حافظهٔ آزادشده از طریق pointer دیگری** (alias) که هنوز `nullptr` نشده.
6. **نشت در `return` زودهنگام یا `throw`**.
7. **`new` در سازنده و نبود `delete` در مخرب** (جلسهٔ ۱۴).
8. **تخصیص بیش از حد بزرگ** → `std::bad_alloc`. برای حجم‌های نامعلوم، `vector` امن‌تر است.

---

## ۸. بهترین شیوه‌ها

- **قانون طلایی:** کد روزمره‌تان هیچ `new`/`delete` خامی نداشته باشد.
- اگر مجبورید: هر `new` دقیقاً یک `delete` در همان تابع یا در مخرب همان کلاس.
- بعد از `delete` فوراً `p = nullptr;`.
- مالکیت را مستند کنید: کدام تابع مسئول آزادسازی است.
- از `std::make_unique` (جلسهٔ ۳۶) برای مالکیت منفرد استفاده کنید.
- در تست‌ها با `-fsanitize=address` کامپایل کنید تا نشتی و استفادهٔ بعد از آزادسازی را زود ببینید:

```bash
g++ -std=c++17 -g -fsanitize=address -o app main.cpp
```

---

## ۹. خلاصه

- stack خودکار است، heap دستی و پویا.
- `new T` ↔ `delete`، `new T[n]` ↔ `delete[]`.
- `new int` مقدار نامعلوم، `new int()` صفر.
- دام‌ها: نشتی، dangling، double free، `delete` اشتباه، نشت در مسیر خطا.
- بعد از `delete` همیشه `nullptr`.
- `std::vector` و `std::string` و در آینده smart pointerها مسئولیت را از شما می‌گیرند.
