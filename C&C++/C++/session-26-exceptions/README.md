# جلسهٔ ۲۶ — مدیریت استثنا

> خطا را نمی‌شود نادیده گرفت؛ یا برمی‌گردانی، یا پرتاب می‌کنی.

---

## اهداف این جلسه

1. `throw`/`try`/`catch` را درست به کار ببرید.
2. انواع استثنای استاندارد و `what()` را بشناسید.
3. استثنای سفارشی با اطلاعات اضافه بسازید.
4. بفهمید در سازنده چه اتفاقی می‌افتد وقتی استثنا پرتاب می‌شود.
5. با `noexcept` و امنیت استثنا (exception safety) آشنا شوید.

---

## ۱. سه کلمه

```cpp
double divide(double a, double b) {
    if (b == 0.0) {
        throw std::invalid_argument("تقسیم بر صفر مجاز نیست");   // ۱) پرتاب
    }
    return a / b;
}

try {                                    // ۲) محافظت
    std::cout << divide(1.0, 0.0);
} catch (const std::invalid_argument& error) {   // ۳) گرفتن
    std::cout << error.what();
}
```

- `throw` کنترل را از تابع خارج می‌کند و به نزدیک‌ترین `catch` سازگار می‌رساند.
- `catch` با **نوع** انتخاب می‌شود، نه با ترتیب کد.
- اگر هیچ `catch` سازگاری نباشد، `std::terminate` صدا زده می‌شود و برنامه می‌میرد.

تفاوت با `bool`: مقدار بازگشتی `bool` را می‌شود نادیده گرفت (`divide(1,0);` بدون بررسی). استثنا را نمی‌شود نادیده گرفت — اگر نگرفته باشید، برنامه متوقف می‌شود یا به لایهٔ بالاتر می‌رود. همین، دلیل اصلی استفاده از استثنا برای خطاهای «غیرمنتظره» است.

---

## ۲. انواع استاندارد

| نوع | کاربرد |
|---|---|
| `std::invalid_argument` | آرگومان نامعتبر (`stoi("abc")`) |
| `std::out_of_range` | اندیس یا محدوده (`vector::at`، `stoi`) |
| `std::runtime_error` | خطای زمان اجرا با پیام |
| `std::logic_error` | خطای برنامه‌نویسی |
| `std::bad_alloc` | کمبود حافظه (`new`) |

همه از `std::exception` مشتق می‌شوند و `what()` دارند:

```cpp
catch (const std::exception& error) {
    std::cerr << error.what() << "\n";
}
```

`what()` یک `const char*` برمی‌گرداند. پیام آن پیاده‌سازی‌محور است (مثلاً `vector::_M_range_check`)، پس روی **متن** آن تست ننویسید؛ روی **نوع** آن تکیه کنید.

---

## ۳. ترتیب catch

```cpp
try {
    // ...
} catch (const std::invalid_argument& error) {   // مشتق‌تر اول
} catch (const std::exception& error) {          // پایه بعد
}
```

اگر ترتیب را برعکس کنید، شاخهٔ دوم هرگز اجرا نمی‌شود — و کامپایلر با `-Wall` هشدار می‌دهد. قاعده: **از خاص به عام**.

`catch (...)` همه‌چیز را می‌گیرد، ولی به شیء دسترسی ندارد. فقط برای پاکسازی نهایی یا مرز سیستم استفاده کنید.

### گرفتن با reference

```cpp
catch (const std::exception& error)     // ✅ بدون کپی، حفظ نوع واقعی
catch (std::exception error)            // ❌ برش شیء!
```

گرفتن با ارزش، همان برش جلسهٔ ۲۲ را تکرار می‌کند: اطلاعات استثنای مشتق از دست می‌رود.

---

## ۴. استثنای سفارشی

```cpp
class ValidationError : public std::runtime_error {
public:
    ValidationError(const std::string& message, const std::string& field)
        : std::runtime_error(message), field_(field) { }

    const std::string& field() const { return field_; }

private:
    std::string field_;
};
```

سه قاعده:

1. از `std::runtime_error` (یا `std::logic_error`) مشتق شوید تا `catch (std::exception&)` آن را بگیرد.
2. پیام را به سازندهٔ پایه بدهید؛ `what()` خودکار کار می‌کند.
3. اطلاعات اضافه را در عضو نگه دارید و با getter بدهید.

خروجی واقعی `02_custom_exception.cpp`:

```
--- ساخت معتبر ---
Saeed ، 30

--- سن نامعتبر ---
ValidationError: سن باید بین 0 و 150 باشد (فیلد: age)
سن هنوز: 30 (تغییر نکرد)

--- نام خالی ---
از طریق std::exception: نام نباید خالی باشد

--- سازندهٔ نامعتبر ---
ساخت شیء شکست خورد: سن باید بین 0 و 150 باشد (فیلد: age)

نتیجه: شیء نامعتبر هرگز ساخته نشد.
```

نکتهٔ طلایی: `setAge(200)` استثنا داد و **سن تغییر نکرد**. قاعدهٔ «اول بررسی، بعد نوشتن» از جلسهٔ ۱۵ همین‌جا هم کار می‌کند.

---

## ۵. استثنا در سازنده

```cpp
Temperature(double celsius) : sensor_("دماسنج"), celsius_(celsius) {
    if (celsius < kAbsoluteZero) {
        throw std::invalid_argument("دما زیر صفر مطلق است");
    }
}
```

چه اتفاقی می‌افتد:

1. اعضا (`sensor_`) ساخته می‌شوند.
2. بدنهٔ سازنده اجرا می‌شود و استثنا می‌دهد.
3. **مخرب اعضای ساخته‌شده** اجرا می‌شود (`~Resource`).
4. **مخرب خود `Temperature` اجرا نمی‌شود** — چون شیء هرگز کامل نشد.
5. استثنا به `catch` می‌رسد.

خروجی واقعی `03_ctor_exception.cpp`:

```
--- ساخت معتبر ---
    تخصیص منبع: دماسنج
    بدنهٔ سازنده: دما پذیرفته شد
  celsius = 25
    مخرب Temperature
    آزادسازی منبع: دماسنج

--- ساخت نامعتبر ---
    تخصیص منبع: دماسنج
    آزادسازی منبع: دماسنج
  گرفته شد: دما زیر صفر مطلق است

--- noexcept ---
  safeDivide(10, 4) = 2.5
  safeDivide(10, 0) = 0 (بدون استثنا)

صفر مطلق: -273.15°C
```

در بخش نامعتبر، «آزادسازی منبع» **بدون** «مخرب Temperature» آمد — دقیقاً همان چیزی که باید باشد. این پایهٔ RAII است (جلسهٔ ۳۸): منابع با تخریب آزاد می‌شوند، حتی وقتی استثنا رخ می‌دهد.

### هرگز در مخرب throw نکنید

مخرب‌ها به‌طور پیش‌فرض `noexcept` هستند. اگر در مخرب استثنا پرتاب شود و استثنای دیگری در جریان باشد، `std::terminate` اجرا می‌شود. اگر کاری در مخرب ممکن است شکست بخورد، آن را در یک تابع جدا با گزارش خطا انجام دهید.

---

## ۶. `noexcept`

```cpp
double safeDivide(double a, double b) noexcept;   // تعهد: پرتاب نمی‌کند
```

- اگر تابعی که `noexcept` است استثنا پرتاب کند، `std::terminate` اجرا می‌شود.
- `noexcept` به کامپایلر اجازهٔ بهینه‌سازی می‌دهد (مخصوصاً در `std::vector` هنگام رشد).
- سازندهٔ انتقال و مخرب باید `noexcept` باشند؛ این برای کارایی کانتینرها مهم است (جلسهٔ ۳۷).

`noexcept` را روی توابعی بگذارید که **قطعاً** پرتاب نمی‌کنند، نه برای «احتیاط».

## ۸. اشتباهات رایج

1. **گرفتن با ارزش**: `catch (std::exception e)` → برش و از دست رفتن اطلاعات.
2. **ترتیب غلط**: `catch (std::exception&)` قبل از نوع مشتق → شاخهٔ دوم مرده.
3. **`catch (...)` به‌عنوان تنها راه** → نمی‌دانید چه شد و چرا.
4. **استثنا برای کنترل جریان عادی** → کند و خوانایی را خراب می‌کند. برای «عدد پیدا نشد» در حلقه، `bool` یا `optional` بهتر است.
5. **فراموش کردن `throw;`** در catch برای انتقال به بالا: `throw;` استثنای جاری را دوباره پرتاب می‌کند؛ `throw error;` یک کپی می‌سازد و نوع ایستا را از دست می‌دهد.
6. **throw در مخرب** → خطر `std::terminate`.
7. **گرفتن استثنا و بلعیدن آن** بدون لاگ یا اقدام → خطا بی‌صدا گم می‌شود.
8. **تخصیص منبع بدون RAII** → با استثنا نشت می‌کند (جلسهٔ ۳۸).
9. **پرتاب اشاره‌گر** (`throw new MyError()`) → چه کسی `delete` می‌کند؟ همیشه با ارزش پرتاب کنید.
10. **تست بر اساس متن `what()`** → بین کامپایلرها و نسخه‌ها تغییر می‌کند.

---

## ۹. بهترین شیوه‌ها

- استثنای سفارشی از `std::runtime_error` یا `std::logic_error` مشتق شود.
- همیشه با `const&` بگیرید.
- از خاص به عام بچینید.
- `throw;` برای انتقال، `throw NewType(...)` برای تبدیل لایه.
- سازنده‌ای که استثنا می‌دهد باید قبل از `throw` هیچ منبع خامی نگیرد — یا از RAII استفاده کند.
- در مخرب هرگز throw نکنید؛ اگر لازم است، تابع `close()` جدا بگذارید.
- `noexcept` را صادقانه اعلام کنید، نه برای ظاهر.
- پیام استثنا باید بگوید **چه چیزی** و **کجا** شکست، نه فقط «خطا».

---

## ۱۰. خلاصه

- `throw` کنترل را به `catch` سازگار می‌رساند؛ بدون catch، برنامه متوقف می‌شود.
- استثناهای استاندارد از `std::exception` می‌آیند و `what()` دارند.
- استثنای سفارشی: مشتق از `std::runtime_error` + اطلاعات اضافه.
- سازنده‌ای که استثنا می‌دهد، شیء را نمی‌سازد ولی اعضای ساخته‌شده را آزاد می‌کند.
- `catch` با `const&`، از خاص به عام، و `noexcept` فقط برای توابع ایمن.
