# جلسهٔ ۳۸ — اصل RAII

> Resource Acquisition Is Initialization: منبع را در سازنده بگیر، در مخرب آزاد کن، بقیه را به کامپایلر بسپار.

---

## اهداف این جلسه

1. اصل RAII و دلیل کارکردش را بفهمید.
2. کلاس نگهبان منبع بنویسید که در مسیر استثنا هم آزادسازی کند.
3. کپی را برای منابع یکتا ممنوع کنید.
4. `std::lock_guard` و `unique_ptr` را به‌عنوان نمونه‌های آمادهٔ RAII بشناسید.
5. قانون صفر را در عمل ببینید.

---

## ۱. مشکلی که RAII حل می‌کند

```cpp
void broken() {
    openFile();
    doWork();        // اگر اینجا استثنا بدهد...
    closeFile();     // ...این خط اجرا نمی‌شود
}
```

هر `return` زودهنگام، هر `throw` و هر `break` یک نقطهٔ فراموشی است. RAII این را حل می‌کند: **تضمین زبان** این است که وقتی کنترل از دامنه خارج شود — به هر دلیلی — مخرب اشیای محلی اجرا می‌شود.

```cpp
void safe() {
    FileGuard guard("data.txt");   // منبع در سازنده گرفته شد
    doWork();                      // حتی با استثنا...
}                                  // ...مخرب guard اجرا می‌شود
```

این سازوکار «stack unwinding» نام دارد و پایهٔ `unique_ptr`، `shared_ptr`، `std::fstream`، `std::lock_guard` و `std::vector` است.

## ۲. اولین نگهبان

```cpp
class Session {
public:
    explicit Session(const std::string& user) : user_(user) {
        // گرفتن منبع
    }
    ~Session() {
        // آزاد کردن منبع
    }
};
```

خروجی واقعی `01_raii_wrapper.cpp`:

```
--- مسیر موفق ---
  + باز کردن نشست: Saeed
    کار در نشست Saeed
    کار تمام شد
  - بستن نشست: Saeed
--- مسیر خطا ---
  + باز کردن نشست: Ali
    کار در نشست Ali
  - بستن نشست: Ali
  گرفته شد: کار شکست خورد
--- خروج زودهنگام ---
  + باز کردن نشست: Sara
    کار در نشست Sara
    کار تمام شد
  - بستن نشست: Sara
در هر سه مسیر، نشست بسته شد.
```

به ترتیب در مسیر خطا دقت کنید: «بستن نشست» **قبل** از «گرفته شد» چاپ شد. یعنی مخرب در حین خروج از دامنه، قبل از رسیدن به `catch`، اجرا شد. این دقیقاً همان تضمینی است که `delete` دستی ندارد.

## ۳. نگهبان فایل

```cpp
class FileWriter {
public:
    explicit FileWriter(const fs::path& path) : path_(path), stream_(path) {
        if (!stream_) {
            throw std::runtime_error("باز کردن فایل ناموفق بود");
        }
    }
    ~FileWriter() {
        if (stream_.is_open()) {
            stream_.close();
        }
    }
    FileWriter(const FileWriter&) = delete;             // یک فایل، یک نویسنده
    FileWriter& operator=(const FileWriter&) = delete;
};
```

سه نکته:

1. **در سازنده بررسی کنید.** اگر منبع گرفته نشد، استثنا بدهید تا شیء «نیمه‌ساخته» وجود نداشته باشد.
2. **در مخرب هرگز استثنا ندهید.** مخرب‌ها `noexcept` هستند و استثنا در آن‌ها `std::terminate` می‌آورد (جلسهٔ ۲۶).
3. **کپی را ممنوع کنید.** دو نگهبان روی یک فایل، یعنی دو بار بستن.

خروجی واقعی `02_raii_file_guard.cpp`:

```
--- نوشتن موفق ---
  + فایل باز شد
  - فایل بسته شد
--- خطا در میانهٔ کار ---
  + فایل باز شد
  - فایل بسته شد
  گرفته شد: خطای شبیه‌سازی‌شده
--- خواندن محتوای فایل ---
  1: خط سوم
  تعداد خطوط: 1
```

چرا فقط «خط سوم» ماند؟ چون `std::ofstream(path)` بدون `ios::app` فایل را **بازنویسی** می‌کند. بلوک دوم فایل را از نو باز کرد، یک خط نوشت و بعد استثنا داد. نکتهٔ مهم این است که در همان مسیر خطا هم «فایل بسته شد» چاپ شد و محتوای نوشته‌شده flush شد.

## ۴. نمونه‌های آماده در کتابخانهٔ استاندارد

| کلاس | منبعی که مدیریت می‌کند |
|---|---|
| `std::unique_ptr` / `std::shared_ptr` | حافظهٔ پویا |
| `std::fstream` / `ifstream` / `ofstream` | فایل |
| `std::lock_guard` / `unique_lock` | قفل `mutex` |
| `std::vector` / `std::string` | حافظهٔ پویا |
| `std::jthread` (C++20) | نخ |

`std::lock_guard` الگوی RAII را در خالص‌ترین شکل نشان می‌دهد:

```cpp
{
    const std::lock_guard<std::mutex> guard(mutex);   // قفل شد
    // ... کار با دادهٔ مشترک ...
}                                                      // قفل آزاد شد
```

بدون `lock_guard` باید یادتان باشد در **همهٔ** مسیرهای خروج `unlock` بزنید — و فراموش می‌کنید.

## ۵. قانون صفر

```cpp
class Report {
    std::string title_;
    std::vector<Row> rows_;
    std::unique_ptr<Connection> connection_;
};
```

هیچ مخرب، کپی یا انتقالی ننوشتید — و همه‌چیز درست کار می‌کند، چون اعضا خودشان RAII هستند. این «قانون صفر» است: **اگر هر عضو منبعش را مدیریت کند، کلاس شما هیچ کاری لازم ندارد.**

قانون پنج (جلسهٔ ۳۷) فقط برای کلاس‌هایی است که خودشان مستقیماً منبع خام دارند.

## ۷. اشتباهات رایج

1. **آزادسازی دستی در چند نقطه** → یک مسیر فراموش می‌شود.
2. **استثنا در مخرب** → `std::terminate`.
3. **کپی‌پذیر گذاشتن نگهبان** → دو بار آزادسازی.
4. **گرفتن منبع در بدنهٔ سازنده بعد از کار خطرناک** → اگر بعدش استثنا بدهد، منبع نشت می‌کند. اول بگیرید، بعد کار کنید.
5. **`close()` صریح و بعد استفاده از شیء** → وضعیت نامعتبر؛ بگذارید مخرب کارش را بکند.
6. **نگهبان با طول عمر کمتر از منبع** → آزادسازی زودهنگام.
7. **`delete this`** → ضدالگوی RAII.
8. **فراموش کردن `is_open`/`operator bool` بعد از باز کردن** → ادامه دادن با جریان نامعتبر.

## ۸. بهترین شیوه‌ها

- هر منبع خام را در یک کلاس کوچک بپیچید (`FileHandle`، `Socket`، `Session`).
- منبع را در لیست مقداردهی سازنده بگیرید، نه در بدنه.
- مخرب را ساده و بدون استثنا نگه دارید.
- کپی را ممنوع و انتقال را (در صورت نیاز) پیاده کنید.
- برای منابع معمول از انواع آمادهٔ استاندارد استفاده کنید؛ چرخ را دوباره نسازید.

---

## ۹. خلاصه

- RAII: گرفتن در سازنده، آزادسازی در مخرب.
- stack unwinding تضمین می‌کند مخرب در مسیر استثنا هم اجرا شود.
- نگهبان باید غیرقابل‌کپی باشد و در سازنده شکست را گزارش کند.
- `unique_ptr`، `fstream` و `lock_guard` نمونه‌های آمادهٔ RAII هستند.
- قانون صفر: اگر اعضا RAII باشند، کلاس شما هیچ مخربی لازم ندارد.

```
--- عملیات کند ---
```

1. با RAII لازم نیست در پایان هر بلوک یادتان باشد گزارش را چاپ کند.
2. `std::chrono::steady_clock` برای اندازه‌گیری مدت مناسب است (ساعت دیواری نیست).
3. `= delete` برای کپی، از دوبار گزارش‌دادن جلوگیری می‌کند.
