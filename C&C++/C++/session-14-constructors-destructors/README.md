# جلسهٔ ۱۴ — سازنده، مخرب و ترتیب ساخت

> شیء بدون سازنده، مثل ماشینی است که ممکن است با پیچ‌های شل از کارخانه بیرون بیاید؛ سازنده اجازه نمی‌دهد.

---

## اهداف این جلسه

1. بدانید **سازنده** (constructor) چیست و چرا جای `open()`/`init()` را می‌گیرد.
2. سه نوع سازنده را بنویسید: پیش‌فرض، پارامتری و **واگذارکننده** (delegating).
3. **لیست مقداردهی اولیه** را درست به کار ببرید و فرقش را با انتساب در بدنه بفهمید.
4. **سازندهٔ کپی** را تشخیص دهید و بدانید کجا فراخوانی می‌شود.
5. **مخرب** (destructor) را بشناسید و ترتیب دقیق ساخت و تخریب را پیش‌بینی کنید.

---

## ۱. سازنده چیست؟

سازنده تابعی است که **هنگام ساخت شیء** و **قبل از هر استفاده‌ای** اجرا می‌شود. سه ویژگی دارد:

- نامش عیناً نام کلاس است.
- نوع بازگشتی ندارد (حتی `void` هم نمی‌نویسیم).
- از بیرون قابل فراخوانی نیست؛ فقط هنگام ساخت شیء اجرا می‌شود.

```cpp
class BankAccount {
public:
    BankAccount(const std::string& ownerName, double initialAmount)
        : owner_(ownerName), balance_(initialAmount < 0.0 ? 0.0 : initialAmount) {
    }

private:
    std::string owner_;
    double balance_ = 0.0;
};

BankAccount account("Saeed", 100.0);   // سازنده همین‌جا اجرا شد
```

در جلسهٔ ۱۳ برای آماده‌سازی حساب یک متد `open()` نوشتیم. مشکل آن این بود که:

```cpp
BankAccount account;          // ساخته شد، ولی هنوز «باز» نیست
account.deposit(50);          // باید در هر متد isOpen_ را چک کنیم
```

با سازنده، این حالت **وجود ندارد**: شیء یا ساخته نمی‌شود، یا از لحظهٔ تولد معتبر است. این همان چیزی است که در تمرین جلسهٔ ۱۳ هم دیدید: `Counter` بدون `setLimits` هم کار می‌کرد، ولی مجبور بودیم محدودهٔ پیش‌فرض را در ذهن نگه داریم.

---

## ۲. سه نوع سازنده

### الف) سازندهٔ پیش‌فرض

سازنده‌ای که هیچ پارامتری نمی‌گیرد:

```cpp
BankAccount() {
    std::cout << "[ساخت] حساب پیش‌فرض\n";
}
```

اگر **هیچ سازنده‌ای** ننویسید، کامپایلر یک سازندهٔ پیش‌فرض خالی برایتان می‌سازد. ولی به‌محض نوشتن یک سازندهٔ دیگر، آن سازندهٔ خودکار حذف می‌شود و `BankAccount a;` دیگر کامپایل نمی‌شود. در کد این جلسه، سازندهٔ پیش‌فرض را **صریح** نوشتیم تا هم چاپ داشته باشد و هم `BankAccount a;` معتبر بماند.

### ب) سازندهٔ پارامتری

```cpp
BankAccount(const std::string& ownerName, double initialAmount)
    : owner_(ownerName), balance_(initialAmount < 0.0 ? 0.0 : initialAmount) {
```

توجه کنید اعتبارسنجی **داخل سازنده** است، نه در `main`. هر راهی که شیء ساخته شود، قاعده یک‌جا اعمال می‌شود — همان اصل جلسهٔ ۱۳.

### پ) سازندهٔ واگذارکننده (delegating constructor)

در C++11 به بعد، یک سازنده می‌تواند کار را به سازندهٔ دیگر همان کلاس بسپارد:

```cpp
BankAccount(const std::string& ownerName)
    : BankAccount(ownerName, 0.0) {          // واگذاری
}
```

این بهتر از تکرار منطق است: اگر روزی اعتبارسنجی عوض شود، فقط یک جا تغییر می‌کند. سازندهٔ واگذارکننده **اول** سازندهٔ مقصد را کامل اجرا می‌کند، بعد بدنهٔ خودش.

## ۳. لیست مقداردهی اولیه در برابر انتساب در بدنه

این دو کد خروجی یکسان می‌دهند، ولی یکی دو بار کار می‌کند و دیگری یک بار:

```cpp
// الف) بدنه — هر عضو اول با مقدار پیش‌فرض ساخته می‌شود، بعد مقدار می‌گیرد
ServerByAssignment(const std::string& name, int port) {
    name_ = name;                                  // default ctor + assignment
    label_ = name + ":" + std::to_string(port);    // default ctor + assignment
    port_ = port;
}

// ب) لیست — هر عضو مستقیماً با مقدار نهایی ساخته می‌شود
ServerByInitList(const std::string& name, int port)
    : name_(name), label_(name + ":" + std::to_string(port)), port_(port) {
}
```

برای `int` فرقی نمی‌کند، ولی برای `std::string` نسخهٔ (الف) یک رشتهٔ خالی می‌سازد، بعد آن را دور می‌ریزد. در پروژه‌های واقعی این کار مرتب تکرار می‌شود و هزینه جمع می‌شود.

### دو مورد که **فقط** با لیست ممکن است

```cpp
class Measurement {
public:
    Measurement(const std::string& sensor, double value)
        : sensor_(sensor), unit_('C'), value_(value) {
    }

private:
    const std::string& sensor_;   // reference
    const char unit_;             // const
    double value_;
};
```

- عضو `const` را نمی‌توان در بدنه مقدار داد؛ باید همان‌جا ساخته شود.
- عضو `reference` هم باید در تولد به یک شیء بسته شود و بعداً قابل تغییر نیست.

اگر بنویسید `unit_ = 'C';` داخل بدنه، کامپایلر خطا می‌دهد: «assignment of read-only member».

### ترتیب مقداردهی همیشه ترتیب **اعلان** است، نه ترتیب نوشتن در لیست

```cpp
class Ordered {
private:
    int a_;   // اول ساخته می‌شود
    int b_;   // دوم
public:
    Ordered() : b_(2), a_(1) {}   // ⚠ گمراه‌کننده است؛ باز هم a_ قبل از b_ ساخته می‌شود
};
```

کامپایلر با `-Wall` هشدار `-Wreorder` می‌دهد. راه درست: لیست را همیشه به همان ترتیب اعلان بنویسید. اگر یک عضو از مقدار عضو دیگر استفاده می‌کند، این تفاوت تبدیل به باگ می‌شود.

## ۴. سازندهٔ کپی

وقتی از روی شیء موجود، شیء تازه می‌سازید، سازندهٔ کپی اجرا می‌شود:

```cpp
Machine copy = original;      // copy constructor
void print(Machine m);        // عبور با ارزش → کپی
Machine makeCopy() { ... }    // return با ارزش → کپی/انتقال
```

```cpp
Machine(const Machine& other)
    : name_(other.name_ + " (کپی)"),
      engine_(other.engine_),      // اعضا هم با سازندهٔ کپی خودشان کپی می‌شوند
      wheel_(other.wheel_) {
}
```

اگر سازندهٔ کپی ننویسید، کامپایلر یکی می‌سازد که **عضو به عضو** کپی می‌کند (shallow copy). برای کلاس‌هایی که فقط `std::string` و `double` دارند کافی است. برای کلاس‌هایی که **منبع خام** دارند (`int*` از `new`) فاجعه است و باید خودتان بنویسیدش — موضوع جلسهٔ ۳۷ (قانون پنج).

> ضرر کپی را همین‌جا ببینید: در خروجی برنامه، ساخت کپی دو خط «کپی قطعه» تولید می‌کند. اگر تابعی `Machine` را با ارزش بگیرد، این هزینه در هر فراخوانی تکرار می‌شود. راه‌حل: `const Machine&`.

## ۵. مخرب

مخرب تابعی است که **هنگام از بین رفتن شیء** اجرا می‌شود:

```cpp
~Machine() {
    std::cout << "  تخریب بدنهٔ " << name_ << "\n";
}
```

- نامش `~` + نام کلاس است.
- پارامتر ندارد و چیزی برنمی‌گرداند.
- **فقط یک مخرب** می‌شود داشت (نه overload).
- برای آزادسازی منابع است: حافظه، فایل، قفل، اتصال شبکه.

زمان اجرای مخرب:

| موقعیت | مخرب کِی اجرا می‌شود |
|---|---|
| پایان بلوک `{}` | خروج از بلوک، به ترتیب **معکوس** ساخت |
| پایان `main` | اشیاء محلی `main` |
| `delete ptr` | هنگام آزادسازی شیء روی heap |
| استثنا در بلوک | در حین «باز کردن پشته» (جلسهٔ ۲۶) |

در این دوره از `new`/`delete` خام استفاده نمی‌کنیم، ولی بدانید مخرب دقیقاً به همین دلیل هست که RAII کار می‌کند (جلسهٔ ۳۸).

---

## ۶. ترتیب ساخت و تخریب — دقیقاً برعکس

قاعده را حفظ کنید؛ در مصاحبه‌ها و در دیباگ نشتی‌ها بارها می‌بینید:

1. **پایه‌ها** قبل از اعضا (جلسهٔ ۲۰).
2. **اعضا** به ترتیب اعلان.
3. **بدنهٔ سازنده** آخر.
4. تخریب: بدنهٔ مخرب، بعد اعضا به ترتیب **معکوس** اعلان، بعد پایه‌ها.

خروجی واقعی `03_ctor_dtor_order.cpp`:

```
    ساخت قطعه: موتور
    ساخت قطعه: چرخ
  ساخت بدنهٔ ماشین الف
```

اعضای `Machine` به این ترتیب اعلان شده‌اند: `name_`، `engine_`، `wheel_`. پس `engine_` قبل از `wheel_` ساخته می‌شود و هنگام تخریب، `wheel_` قبل از `engine_` از بین می‌رود:

```
  تخریب بدنهٔ ماشین الف (کپی)
    تخریب قطعه: چرخ
    تخریب قطعه: موتور
```

بدنهٔ مخرب **قبل از** اعضا اجرا می‌شود؛ یعنی وقتی `~Machine` چاپ می‌کند، اعضا هنوز زنده‌اند. این نکته مهم است: در بدنهٔ مخرب هنوز می‌توانید با `engine_` کار کنید، ولی بعد از آن دسترسی ندارید.

### ۷.۲ `02_initializer_list.cpp`

```
با انتساب در بدنه : api.example.com:8080
با لیست مقداردهی  : api.example.com:8080
حسگر ۱: 21.5°C

نتیجه: لیست مقداردهی، ساخت اضافه و انتساب دوباره را حذف می‌کند.
```

خروجی یکسان است — **تفاوت در تعداد عملیات است، نه در نتیجه**. برای دیدن تفاوت واقعی می‌توانید نسخهٔ (الف) را با `std::string` بزرگ‌تر و شمارندهٔ سازندهٔ کپی تست کنید.

نکتهٔ دیگر: `Measurement` یک `const std::string&` نگه می‌دارد که به `sensorName` در `main` بسته شده است. اگر `Measurement` بیشتر از `sensorName` زنده بماند، مرجع معلق (dangling) می‌شود — یکی از دلایلی که نگه‌داشتن reference در کلاس خطرناک است.

### ۷.۳ `03_ctor_dtor_order.cpp`

```
--- شروع بلوک ---
    ساخت قطعه: موتور
    ساخت قطعه: چرخ
  ساخت بدنهٔ ماشین الف

--- ساخت کپی ---
    کپی قطعه: موتور
    کپی قطعه: چرخ
  ساخت بدنهٔ ماشین الف (کپی)

--- پایان بلوک ---
  تخریب بدنهٔ ماشین الف (کپی)
    تخریب قطعه: چرخ
    تخریب قطعه: موتور
  تخریب بدنهٔ ماشین الف
    تخریب قطعه: چرخ
    تخریب قطعه: موتور
--- بعد از بلوک ---

نتیجه: ساخت از درون به بیرون، تخریب دقیقاً برعکس.
```

دو نکته که فقط با اجرا معلوم می‌شود:

1. `Machine copy = original;` **هیچ‌وقت** سازندهٔ پارامتری را صدا نمی‌زند؛ مستقیم سراغ سازندهٔ کپی می‌رود. اگر `Machine(const Machine&)` را حذف کنیم، همان خروجی بدون خط «(کپی)» را می‌بینیم.
2. `copy` بعد از `original` ساخته شده، پس **قبل از** آن تخریب می‌شود. اگر مخرب `copy` به داده‌ای وابسته بود که `original` آزاد می‌کند، این ترتیب نجاتش می‌داد.

## ۸. اشتباهات رایج

1. **`void` نوشتن برای سازنده** — `void BankAccount()` یک تابع معمولی است، نه سازنده.
2. **فراموش کردن اینکه نوشتن یک سازنده، سازندهٔ پیش‌فرض را حذف می‌کند** — بعد `BankAccount a;` خطا می‌دهد. اگر لازم است، `BankAccount() = default;` بنویسید.
3. **مقداردهی در بدنه برای اعضای `const`/reference** — خطای کامپایل.
4. **نوشتن لیست مقداردهی به ترتیب دلخواه** — ترتیب واقعی از اعلان می‌آید؛ `-Wreorder` هشدار می‌دهد.
5. **مقدار نامعتبر در سازنده بدون بررسی** — `BankAccount("x", -50)` نباید موجودی منفی بسازد.
6. **صدا زدن متد virtual در سازنده/مخرب** — رفتار غیرمنتظره؛ در جلسهٔ ۲۲ توضیح داده می‌شود.
7. **منبع خام بدون مخرب** — `new` در سازنده و فراموشی `delete` در مخرب = نشتی (جلسهٔ ۳۸ و RAII).
8. **کپی گران بدون `const&`** — `void f(Machine m)` در هر فراخوانی کپی می‌سازد.
9. **انتظار اجرای مخرب برای شیء heap بدون `delete`** — مخرب فقط با `delete` یا خروج از scope اجرا می‌شود.

## ۹. بهترین شیوه‌ها

- هر کلاس باید در **همهٔ سازنده‌ها** یک invariant واحد داشته باشد.
- اگر چند سازنده منطق مشترک دارند، از **سازندهٔ واگذارکننده** استفاده کنید.
- همیشه **لیست مقداردهی اولیه** بنویسید، حتی برای `int` — عادت درست، و برای اعضای غیرقابل انتساب اجباری است.
- لیست را به **ترتیب اعلان** بنویسید.
- پارامترها را `const&` بگیرید (به‌جز انواع کوچک مثل `int`/`double`).
- سازنده‌ای که یک پارامتر می‌گیرد و تبدیل ضمنی ناخواسته ایجاد می‌کند را `explicit` کنید:
  ```cpp
  explicit Part(const std::string& name);
  ```
- مخرب را برای آزادسازی منابع بنویسید، نه برای چاپ یا کار منطقی.
- اگر کلاس نباید کپی شود، صریح حذفش کنید: `Timer(const Timer&) = delete;`

---

## ۱۰. خلاصه

- سازنده، شیء را از لحظهٔ تولد معتبر می‌کند؛ `open()`/`init()` دیگر لازم نیست.
- سه نوع: پیش‌فرض، پارامتری، واگذارکننده — و در ادامه سازندهٔ کپی.
- لیست مقداردهی اولیه: ساخت مستقیم، و تنها راه برای اعضای `const` و reference.
- ترتیب ساخت: پایه‌ها → اعضا (ترتیب اعلان) → بدنه.
- ترتیب تخریب: بدنه → اعضا (معکوس) → پایه‌ها.
- مخرب با خروج از scope یا `delete` اجرا می‌شود.

1. مخرب **خودکار** اجرا می‌شود؛ لازم نیست `timer.stop()` صدا بزنید.
2. شیء `blockTimer` داخل `{}` قبل از `totalTimer` تخریب می‌شود، چون دیرتر ساخته شده.
3. اگر `Timer` کپی شود، دو مخرب برای یک بازه گزارش می‌دهند؛ به همین دلیل کپی را `delete` کردیم — اولین نمونهٔ «منبع غیرقابل کپی» که در جلسهٔ ۳۶ به `unique_ptr` می‌رسد.

## ۱۲. قدم بعدی
