# جلسهٔ ۱۳ — کپسوله‌سازی و حفظ حالت معتبر

> کلاس خوب اجازه نمی‌دهد شیء در وضعیت بی‌معنی قرار بگیرد — نه از سر ادب، بلکه چون راهش را بسته است.

---

## اهداف این جلسه

1. مفهوم **کپسوله‌سازی**: داده + رفتار در یک واحد، با مرز مشخص.
2. تفاوت **رابط عمومی** و **پیاده‌سازی خصوصی** را در عمل ببینید.
3. مفهوم **invariant** (قاعدهٔ همیشگی) را بشناسید و در کد حفظ کنید.
4. اعتبارسنجی را در ورودی کلاس انجام دهید، نه در جای‌های پراکندهٔ برنامه.
5. بدانید کپسوله‌سازی چه سودی برای تغییر آیندهٔ کد دارد.

---

## ۱. کپسوله‌سازی چیست؟

کپسوله‌سازی یعنی:

- **داده** و **عملیات مربوط به آن** در یک واحد باشند (کلاس).
- از بیرون فقط یک **رابط کنترل‌شده** دیده شود.
- جزئیات داخلی آزاد باشند تا تغییر کنند، بدون شکستن کد کاربران کلاس.

```cpp
class BankAccount {
public:
    bool deposit(double amount);      // رابط
    bool withdraw(double amount);
    double balance() const;

private:
    double balance_ = 0.0;            // پیاده‌سازی
};
```

کاربر کلاس فقط سه تابع بالا را می‌شناسد. اگر فردا `balance_` را به سنت تبدیل کنید یا یک تاریخچه اضافه کنید، کد کاربر عوض نمی‌شود.

---

## ۲. invariant: قاعده‌ای که همیشه باید برقرار باشد

برای هر کلاس، یک یا چند جمله وجود دارد که باید در **همهٔ لحظات** درست باشد:

| کلاس | invariant |
|---|---|
| `BankAccount` | `balance >= 0` |
| `Temperature` | `celsius >= -273.15` |
| `Person` | `0 <= age <= 150`، `name` غیرخالی |
| `Counter` | `minimum <= value <= maximum` |

اگر invariant بشکند، بقیهٔ متدها نتیجهٔ بی‌معنی می‌دهند. راه حفظ آن ساده است: **تنها راه تغییر وضعیت، متدهایی باشند که قبل از تغییر بررسی می‌کنند.**

---

## ۳. مقایسه: `struct` باز در برابر `class` محافظ

```cpp
struct NaiveTemperature {
    double celsius = 0.0;
};

NaiveTemperature naive;
naive.celsius = -500.0;                 // هیچ‌کس جلوی شما را نمی‌گیرد
```

نتیجهٔ برنامه: `-500°C = -868°F` — از نظر فیزیکی بی‌معنی، ولی کامپایل می‌شود و اجرا هم می‌شود.

```cpp
class Temperature {
public:
    bool setCelsius(double value) {
        if (value < kAbsoluteZero) {
            return false;               // رد می‌شود
        }
        celsius_ = value;
        return true;
    }

    double celsius() const { return celsius_; }
    double fahrenheit() const { return celsius_ * 9.0 / 5.0 + 32.0; }

private:
    static constexpr double kAbsoluteZero = -273.15;
    double celsius_ = 0.0;
};
```

حالا `setCelsius(-300)` مقدار `false` برمی‌گرداند و شیء دست‌نخورده می‌ماند.

**قاعده:** در هر setter، اول اعتبارسنجی، بعد نوشتن. هرگز مقدار نامعتبر را ننویسید و بعد «درستش کنید».

---

## ۴. مقدار بازگشتی `bool` برای شکست

دو الگو برای گزارش خطا در setter وجود دارد:

```cpp
// الف) مقدار بازگشتی bool
bool setScore(double value) {
    if (value < 0.0 || value > 20.0) {
        return false;
    }
    score_ = value;
    return true;
}

// ب) استثنا (جلسهٔ ۲۶)
void setScore(double value) {
    if (value < 0.0 || value > 20.0) {
        throw std::invalid_argument("score out of range");
    }
    score_ = value;
}
```

`bool` برای خطاهای **قابل انتظار** (ورودی کاربر) مناسب است؛ استثنا برای شرایطی که «نباید اتفاق بیفتد» و می‌خواهید برنامه متوقف شود.

> الگوی سوم: setter اصلاً وجود نداشته باشد. اگر یک مقدار فقط در سازنده تعیین شود (مثل `id`)، بهتر است setter نداشته باشد. این کار در جلسهٔ ۱۴ با سازنده کامل می‌شود.

---

## ۵. `const` بخشی از رابط است

```cpp
double balance() const;      // فقط می‌خواند
void deposit(double amount); // تغییر می‌دهد
```

- روی شیء `const` فقط متد `const` قابل فراخوانی است.
- در تابعی که پارامتر `const BankAccount&` می‌گیرد، فقط `balance()` در دسترس است.
- اگر `const` را فراموش کنید، کلاس در کدهای فقط‌خواندنی غیرقابل استفاده می‌شود و مجبور می‌شوید کپی بگیرید.

**قاعده:** هر متدی که اعضا را تغییر نمی‌دهد، `const` بگیرد — از همان ابتدا.

---

## ۶. سود واقعی کپسوله‌سازی

1. **جلوگیری از خرابی**: کاربر نمی‌تواند `balance_` را مستقیم صفر یا منفی کند.
2. **آزادی تغییر**: می‌توانید پیاده‌سازی را عوض کنید (مثلاً `double` به `long long` سنت) بدون تغییر رابط.
3. **مکان واحد برای قاعده**: اعتبارسنجی یک‌جا است، نه در ۱۲ نقطهٔ برنامه.
4. **تست‌پذیری**: رابط کوچک، تست کوچک.
5. **خوانایی**: کسی که `account.withdraw(50)` می‌خواند، منظور را می‌فهمد.

نقطهٔ مقابل: کپسوله‌سازی بیش از حد. اگر برای هر عضو یک getter و setter خام بگذارید، در عمل همان `struct` عمومی دارید با کد بیشتر. فقط چیزی را عمومی کنید که بخشی از **قرارداد** کلاس است.

## ۸. اشتباهات رایج

1. **گذاشتن `public` روی داده** چون «راحت‌تر است» → invariant از بین می‌رود.
2. **اعتبارسنجی بعد از نوشتن**: `balance_ -= amount; if (balance_ < 0) {...}` — دیگر دیر شده.
3. **getter و setter برای همهٔ اعضا** بدون فکر → همان `struct` عمومی با کد اضافه.
4. **فراموش کردن `const`** روی متدهای فقط‌خواندنی.
5. **بازگرداندن مرجع به عضو خصوصی** برای «دسترسی سریع»:
   ```cpp
   std::string& name() { return name_; }   // ❌ حالا از بیرون قابل تغییر است
   ```
   به‌جایش `const std::string& name() const`.
6. **انجام اعتبارسنجی در `main`** به‌جای کلاس → هر مسیر جدید ورود، یک باگ جدید.
7. **پیام خطای بی‌جزئیات**: `false` برگرداندن بدون اینکه معلوم باشد چرا (در پروژه‌های بزرگ‌تر، `enum` خطا یا استثنا بهتر است).

---

## ۹. بهترین شیوه‌ها

- همهٔ اعضای داده را `private` بگذارید، مگر اینکه کلاس واقعاً فقط یک رکورد است.
- رابط را **کوچک** نگه دارید: کمترین کارهایی که کاربر کلاس لازم دارد.
- هر setter: اعتبارسنجی، سپس نوشتن، سپس `return true`.
- متدهای فقط‌خواندنی `const`.
- نام متدها فعل باشد: `deposit`، `withdraw`، `reset` — نه `setBalance`.
- عملیات دامنه‌ای بسازید (`withdraw`) نه دستکاری خام (`setBalance`). عملیات دامنه‌ای می‌تواند قاعده را حفظ کند.

---

## ۱۰. خلاصه

- کپسوله‌سازی = داده + رفتار + مرز کنترل‌شده.
- `invariant` قاعده‌ای است که همیشه باید برقرار باشد؛ فقط متدهای بررسی‌کننده وضعیت را تغییر می‌دهند.
- `bool` برای خطاهای قابل انتظار، استثنا برای شرایط استثنایی.
- متد `const` بخشی از قرارداد کلاس است.
- رابط کوچک و عملیات دامنه‌ای، بهتر از getter/setter برای همه‌چیز.
