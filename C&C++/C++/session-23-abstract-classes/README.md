# جلسهٔ ۲۳ — کلاس انتزاعی، تابع مجازی خالص و اینترفیس

> بعضی کلاس‌ها فقط قرارداد هستند؛ نباید از آن‌ها شیء ساخت.

---

## اهداف این جلسه

1. تابع مجازی خالص (`= 0`) و کلاس انتزاعی را بشناسید.
2. بفهمید چرا کلاس انتزاعی جلوی «فراموش کردن override» را می‌گیرد.
3. اینترفیس در C++ بسازید و با تزریق وابستگی (dependency injection) استفاده کنید.
4. `final` را برای کلاس و متد به کار ببرید.
5. کل فاز شیءگرایی را جمع‌بندی کنید و به پروژهٔ پایان فاز برسید.

---

## ۱. تابع مجازی خالص

```cpp
class Shape {
public:
    virtual double area() const = 0;      // = 0 → خالص
    virtual std::string name() const = 0;
};
```

`= 0` یعنی: «این تابع در این کلاس پیاده‌سازی ندارد؛ هر زیرکلاس **باید** آن را پیاده کند.»

نتیجه: `Shape` یک **کلاس انتزاعی** است:

```cpp
Shape shape;                  // ❌ error: cannot declare variable to be of abstract type
Shape* p = new Shape();       // ❌ همان خطا
const Shape& ref = square;    // ✅ مرجع و اشاره‌گر مجازند
```

`Shape` هنوز می‌تواند:

- مخرب، سازنده، متد غیر virtual و داده داشته باشد.
- پیاده‌سازی مشترک برای متدهای غیر خالص داشته باشد (`describe`، `isBiggerThan`).

تفاوت مهم با جلسهٔ ۲۲:

| حالت | اگر زیرکلاس فراموش کند | نتیجه |
|---|---|---|
| `virtual double area() const { return 0; }` | کامپایل می‌شود | بی‌صدا `0` می‌دهد — باگ |
| `virtual double area() const = 0;` | خطای کامپایل | زیرکلاس انتزاعی می‌ماند |

همین تفاوت، دلیل اصلی استفاده از تابع خالص است: **خطای کامپایل بهتر از نتیجهٔ غلط است.**

---

## ۲. کلاس انتزاعی نیمه‌آماده

کلاس انتزاعی لازم نیست فقط قرارداد باشد؛ می‌تواند منطق مشترک داشته باشد:

```cpp
class Shape {
public:
    virtual ~Shape() = default;
    virtual double area() const = 0;
    virtual std::string name() const = 0;

    void describe() const {
        std::cout << name() << ": " << area() << "\n";
    }

    bool isBiggerThan(const Shape& other) const {
        return area() > other.area();
    }
};
```

`describe` و `isBiggerThan` یک بار نوشته شده‌اند و برای همهٔ شکل‌ها کار می‌کنند، ولی رفتارشان به `area()` هر شکل وابسته است. این الگو (اسکلت در پایه، جزئیات در مشتق) در ادبیات طراحی **Template Method** نام دارد.

---

## ۳. اینترفیس در C++

C++ کلمهٔ `interface` ندارد. اینترفیس = کلاس انتزاعی **بدون داده و بدون پیاده‌سازی**:

```cpp
class ILogger {
public:
    virtual ~ILogger() = default;
    virtual void log(const std::string& level, const std::string& message) = 0;
};
```

قواعد یک اینترفیس خوب:

1. **مخرب virtual** (`= default`).
2. **بدون دادهٔ عضو** — اگر داده دارد، دیگر قرارداد نیست.
3. **همهٔ متدها خالص** (یا حداکثر یکی-دو متد کمکی non-virtual).
4. نام با `I` شروع شود (`ILogger`، `IPayment`) — قرارداد رایج، نه الزام زبان.

در جلسهٔ ۲۱ دیدیم که اینترفیس‌ها کاربرد اصلی و سالم وراثت چندگانه‌اند.

---

## ۴. تزریق وابستگی

```cpp
class UserService {
public:
    explicit UserService(ILogger& logger) : logger_(logger) { }

    bool registerUser(const std::string& name) {
        if (name.empty()) {
            logger_.log("WARN", "نام خالی است");
            return false;
        }
        logger_.log("INFO", "کاربر ثبت شد: " + name);
        return true;
    }

private:
    ILogger& logger_;
};
```

`UserService` نمی‌داند لاگ به کنسول می‌رود، به فایل می‌رود، یا جمع می‌شود. سه سود فوری:

1. **تست**: `CountingLogger` را می‌دهید و بدون هیچ خروجی، رفتار را بررسی می‌کنید.
2. **تغییر بی‌خطر**: لاگ به فایل، بدون تغییر یک خط از `UserService`.
3. **مرز روشن**: وابستگی‌ها در سازنده صریح‌اند، نه پنهان در global.

> `ILogger&` را با reference نگه داشتیم، چون `UserService` مالک لاگ نیست. اگر مالکیت لازم بود، `std::unique_ptr<ILogger>` (جلسهٔ ۳۶).

## ۵. `final`

```cpp
class Square final : public Shape { };    // هیچ‌کس از Square ارث نمی‌برد

class Circle : public Shape {
    double area() const final;            // زیرکلاس Circle نمی‌تواند بازنویسی کند
};
```

دو کاربرد:

- **طراحی**: می‌خواهید رفتار کلاس تضمین‌شده بماند.
- **بهینه‌سازی**: کامپایلر می‌تواند فراخوانی virtual را مستقیم کند (devirtualization).

`final` روی کلاس به کامپایلر اجازهٔ بهینه‌سازی می‌دهد و به خواننده می‌گوید «این‌جا پایان سلسله‌مراتب است».

## ۷. اشتباهات رایج

1. **فراموش کردن پیاده‌سازی یک تابع خالص** → خطای کامپایل هنگام ساخت شیء؛ اگر پیام گنگ بود، دنبال متد جاافتاده بگردید.
2. **مخرب غیر virtual در کلاس انتزاعی** → همان مشکل جلسهٔ ۲۲، حتی اگر کلاس انتزاعی است.
3. **داشتن داده در اینترفیس** → دیگر قرارداد نیست؛ برای دادهٔ مشترک، کلاس پایهٔ غیر اینترفیس بسازید.
4. **صدا زدن تابع خالص در سازنده/مخرب پایه** → UB یا خطا؛ شیء هنوز کامل نیست.
5. **`= 0` روی تابعی که می‌خواهید پیاده‌سازی پیش‌فرض داشته باشد** — می‌توانید `= 0` بدهید **و** پیاده‌سازی جدا بنویسید (نادر، ولی مجاز).
6. **اینترفیس بزرگ** با ۱۵ متد → هر پیاده‌سازی مجبور است همه را بنویسد؛ اینترفیس را کوچک و متمرکز نگه دارید.
7. **تزریق وابستگی با `new` داخل کلاس** → همان کوپلینگ قبلی، فقط جابه‌جا شده.
8. **`final` روی کلاس پایه‌ای که باید توسعه یابد** → سلسله‌مراتب را می‌بندد.

---

## ۸. بهترین شیوه‌ها

- هر «مفهوم پایه» را انتزاعی کنید، نه concrete با پیاده‌سازی خالی.
- کلاس انتزاعی = قرارداد + رفتار مشترک؛ اینترفیس = فقط قرارداد.
- مخرب `virtual` همیشه.
- وابستگی‌ها را از بیرون بدهید (پارامتر سازنده)، داخل کلاس نسازید.
- اینترفیس‌ها را کوچک نگه دارید (چند متد، یک مسئولیت).
- `override` بنویسید، `final` را جاهایی که پایان سلسله‌مراتب است.
- برای تست، پیاده‌سازی «جمع‌کننده» یا «بی‌اثر» از اینترفیس بسازید.

---

## ۹. خلاصه

- `= 0` تابع را خالص و کلاس را انتزاعی می‌کند.
- از کلاس انتزاعی نمی‌شود شیء ساخت، ولی اشاره‌گر و مرجع مجاز است.
- اینترفیس = کلاس انتزاعی بی‌داده با مخرب virtual.
- تزریق وابستگی، کد را تست‌پذیر و قابل تغییر می‌کند.
- `final` پایان سلسله‌مراتب را اعلام می‌کند.

### تمرین ۱ — اینترفیس `IPayment` با دو پیاده‌سازی (متوسط)

`exercises/exercise_01.cpp`: پرداخت با کارت (سقف ۵۰۰) و کیف پول (موجودی اولیه).

```cpp
class IPayment {
public:
    virtual ~IPayment() = default;
    virtual bool pay(double amount) = 0;
    virtual std::string name() const = 0;
    virtual double paidTotal() const = 0;
};
```

```
کارت: pay(80) → موفق
کارت: pay(600) → ناموفق (سقف یا موجودی)
کیف پول: pay(80) → موفق
کیف پول: pay(600) → ناموفق (سقف یا موجودی)

کارت: paid = 80
کیف پول: paid = 80
موجودی کیف پول: 20
مجموع: 160
```

سه نکته:

1. `IPayment` هیچ داده‌ای ندارد؛ هر پیاده‌سازی شمارنده و موجودی خودش را دارد.
2. `paidTotal()` در اینترفیس است تا بتوان مجموع را فقط با `IPayment*` حساب کرد — بدون دانستن نوع واقعی.
3. `pay` **غیر const** است، چون وضعیت را تغییر می‌دهد؛ `paidTotal` **const** است.

1. کلاس انتزاعی `Employee` با:
