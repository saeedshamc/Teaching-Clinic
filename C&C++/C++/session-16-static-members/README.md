# جلسهٔ ۱۶ — اعضای static در کلاس

> بعضی داده‌ها مال شیء نیستند؛ مال کلاس‌اند. `static` راه گفتن همین جمله است.

---

## اهداف این جلسه

1. تفاوت **عضو دادهٔ static** و عضو معمولی را در حافظه ببینید.
2. **تابع static** بنویسید و بدانید چرا `this` ندارد.
3. شمارندهٔ نمونه‌های زنده بسازید (constructor + destructor).
4. الگوی **شناسهٔ یکتا** و **سازندهٔ کارخانه‌ای** را پیاده کنید.
5. با `inline static` (C++17) تعریف و مقداردهی را یک‌جا انجام دهید.

---

## ۱. عضو static چیست؟

عضو معمولی: **یک نسخه برای هر شیء**.
عضو static: **یک نسخه برای کل کلاس**، مشترک بین همهٔ اشیاء.

```cpp
class Widget {
private:
    std::string name_;            // هر شیء نسخهٔ خودش را دارد
    inline static int alive_ = 0; // همهٔ اشیاء یک شمارنده را می‌بینند
};
```

از نظر حافظه، `alive_` در `sizeof(Widget)` حساب نمی‌شود؛ در بخش دادهٔ static برنامه زندگی می‌کند. `Widget a, b;` دو تا `name_` دارد ولی فقط یک `alive_`.

---

## ۲. تعریف و مقداردهی

سه سبک، به ترتیب تاریخ:

```cpp
// الف) C++98 — اعلان در کلاس، تعریف در فایل .cpp
class Old {
    static int count_;        // اعلان
};
int Old::count_ = 0;          // تعریف، دقیقاً یک بار در کل برنامه

// ب) C++17 — inline static، همه‌چیز در هدر
class New {
    inline static int count_ = 0;
};

// پ) برای ثابت‌های زمان کامپایل
class Consts {
    static constexpr int kMax = 100;
};
```

در این دوره از سبک (ب) استفاده می‌کنیم، چون فایل `.cpp` جدا نداریم و از تکرار تعریف و خطای لینک (`multiple definition`) در امان می‌مانیم. اگر `inline` را جا بگذارید و در هدر مقدار بدهید، لینکر شکایت می‌کند — همین اشتباه در پروژه‌های چندفایلی بسیار رایج است (جلسهٔ ۴۳).

---

## ۳. تابع static

```cpp
static int alive() { return alive_; }
```

- `this` ندارد، پس نمی‌تواند به `name_` دسترسی داشته باشد.
- با `Widget::alive()` صدا زده می‌شود — بدون شیء.
- در واقع یک تابع آزاد است که در فضای نام کلاس قرار گرفته.

```cpp
Widget::alive();   // ✅ درست
a.alive();         // کامپایل می‌شود، ولی گمراه‌کننده است
```

تابع static فقط به اعضای static دسترسی دارد. اگر داخلش `name_` بنویسید، خطای کامپایل می‌گیرید: «invalid use of member in static member function».

---

## ۴. شمارش نمونه‌های زنده

الگوی کلاسیک: زیاد کردن در سازنده، کم کردن در مخرب.

```cpp
Widget() {
    ++alive_;
}
~Widget() {
    --alive_;
}
```

خروجی واقعی `01_static_counter.cpp`:

```
شروع: زنده = 0

ساخت A — زنده: 1
ساخت B — زنده: 2
ساخت C در بلوک — زنده: 3
ساخت Widget بدون نام — زنده: 4
داخل بلوک: زنده = 4
تخریب بی‌نام — زنده: 3
تخریب C در بلوک — زنده: 2
بعد از بلوک: زنده = 2
```

دو نکته:

1. تخریب داخل بلوک **معکوس** ترتیب ساخت است (جلسهٔ ۱۴): `بی‌نام` قبل از `C`.
2. اگر سازندهٔ کپی را هم بنویسید، باید آن را هم بشمارید — وگرنه شمارنده از واقعیت جدا می‌شود. به همین دلیل شمارش درست، تمرین خوبی برای دیدن همهٔ مسیرهای ساخت است.

> این شمارنده در پروژه‌های واقعی برای «نشتی منابع» هم استفاده می‌شود: اگر بعد از پایان برنامه `alive > 0` باشد، جایی `delete` جا افتاده است.

## ۵. سازندهٔ کارخانه‌ای (factory)

```cpp
class Temperature {
public:
    static Temperature fromCelsius(double value);
    static Temperature fromFahrenheit(double value);
    static Temperature fromKelvin(double value);

private:
    explicit Temperature(double celsius);
};
```

سه سود:

1. **خوانایی**: `Temperature::fromFahrenheit(98.6)` واضح‌تر از `Temperature(37.0)` است.
2. **اعتبارسنجی متمرکز**: هر سه مسیر به یک سازندهٔ خصوصی می‌رسند که قاعدهٔ صفر مطلق را اعمال می‌کند.
3. **کنترل ساخت**: با `private` کردن سازنده، هیچ‌کس نمی‌تواند بدون واحد، شیء بسازد.

```cpp
Temperature bad(50.0);   // ❌ خطای کامپایل: سازنده private است
```

همین الگو در جلسهٔ ۴۷ به الگوی طراحی Factory می‌رسد.

## ۷. اشتباهات رایج

1. **`inline` را جا گذاشتن** در C++17 → خطای لینک `multiple definition` در پروژهٔ چندفایلی.
2. **تعریف دوبارهٔ عضو static در `.cpp`** وقتی `inline` است → همان خطا از سمت دیگر.
3. **دسترسی به عضو غیر static در تابع static** → خطای کامپایل، چون `this` وجود ندارد.
4. **فراموش کردن شمارش در سازندهٔ کپی/انتقال** → شمارنده دروغ می‌گوید.
5. **استفاده از static به‌عنوان متغیر جهانی پنهان** → همان مشکلات global، با ظاهر شیک‌تر؛ حالت مشترک قابل تغییر، تست را سخت می‌کند.
6. **`static` در هدر بدون `inline` یا `constexpr`** برای متغیر → مشکل تعریف چندگانه.
7. **انتظار پاک شدن شمارنده با پایان یک شیء** — شمارنده به شیء وابسته نیست.
8. **ترتیب ساخت static‌ها بین واحدهای ترجمه** — مبهم است؛ روی آن حساب نکنید.

---

## ۸. بهترین شیوه‌ها

- عضو static را `inline static` تعریف کنید (C++17) مگر دلیل خاصی برای جداسازی داشته باشید.
- ثابت‌های زمان کامپایل: `static constexpr`.
- تابع static فقط برای کاری که به شیء وابسته نیست: شمارش، کارخانه، اعتبارسنجی ورودی، تبدیل واحد.
- شمارندهٔ نمونه‌ها را در **همهٔ** سازنده‌ها (کپی و انتقال هم) و مخرب به‌روز کنید.
- برای شناسهٔ یکتا، شمارنده را در سازنده زیاد کنید و مقدار قبلی را برگردانید (`nextId_++`).
- اگر سازنده را `private` می‌کنید، حتماً یک تابع کارخانه‌ای عمومی بگذارید.

---

## ۹. خلاصه

- عضو static: یک نسخه برای کل کلاس، نه برای هر شیء.
- تابع static: بدون `this`، فقط با اعضای static کار می‌کند.
- شمارندهٔ زنده = سازنده `++`، مخرب `--` (و کپی/انتقال هم بشمارید).
- `inline static` (C++17) تعریف و مقداردهی را یک‌جا می‌کند.
- سازندهٔ کارخانه‌ای + سازندهٔ خصوصی = کنترل کامل روی راه‌های ساخت.

## ۱۰. تمرین‌ها

### تمرین ۱ — تولید شناسهٔ یکتا (متوسط)

`exercises/exercise_01.cpp`: کلاس `Ticket` که شناسه‌اش را از شمارندهٔ static می‌گیرد.

```cpp
explicit Ticket(const std::string& owner);
int id() const;
static int issued();    // تعداد ساخته‌شده
static int lastId();    // آخرین شناسه
```

شمارنده از 1000 شروع می‌شود.

```
Ticket #1000 برای Saeed
Ticket #1001 برای Ali
Ticket #1002 برای مهمان
issued = 3 ، lastId = 1002
```

دو نکتهٔ ریز که در راه‌حل ببینید:

- `id_(nextId_++)` مقدار **قبلی** را می‌دهد و بعد زیاد می‌کند؛ اگر `++nextId_` بنویسید، شناسه‌ها از 1001 شروع می‌شوند.
- `lastId()` مقدار `nextId_ - 1` است، چون `nextId_` همیشه به شناسهٔ **بعدی** اشاره می‌کند. قبل از ساخت اولین بلیت، `lastId` عدد بی‌معنای `999` می‌دهد — این را در خروجی می‌بینید. اگر این حالت مهم است، باید `issued_ == 0` را جدا بررسی کنید.

راه‌حل: `exercises/exercise_01_solution.cpp`
