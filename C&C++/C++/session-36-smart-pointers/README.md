# جلسهٔ ۳۶ — اشاره‌گرهای هوشمند

> `new` و `delete` را فراموش کنید؛ نه چون بد هستند، چون **مالکیت** را نمی‌گویند.

---

## اهداف این جلسه

1. مشکل `new`/`delete` خام را در مسیرهای استثنا ببینید.
2. `unique_ptr` و انتقال مالکیت را به کار ببرید.
3. `shared_ptr` و شمارش مراجع را بفهمید.
4. با `weak_ptr` چرخهٔ مالکیت را بشکنید.
5. قاعدهٔ تصمیم‌گیری بین سه اشاره‌گر را بدانید.

---

## ۱. مشکل اصلی `new`/`delete`

```cpp
void broken() {
    Resource* resource = new Resource("فایل");
    resource->use();
    if (somethingFails()) {
        throw std::runtime_error("خطا");   // ❌ delete اجرا نمی‌شود
    }
    delete resource;
}
```

سه مشکل:

1. **نشت در مسیرهای خروج زودهنگام** — هر `return` یا `throw` جدید یک نقطهٔ نشت است.
2. **مالکیت نامعلوم** — از امضای تابع نمی‌فهمید چه کسی باید `delete` کند.
3. **دو آزادسازی** — اگر دو بخش کد فکر کنند مالک‌اند، برنامه کرش می‌کند.

راه‌حل: مالکیت را در **نوع** بیان کنید. `std::unique_ptr<T>` می‌گوید «یک مالک»، `std::shared_ptr<T>` می‌گوید «چند مالک»، `T*` می‌گوید «هیچ‌کس».

---

## ۲. `unique_ptr` — مالکیت انحصاری

```cpp
auto resource = std::make_unique<Resource>("فایل");
resource->use();      // عملگر -> مثل اشاره‌گر خام
// delete خودکار در پایان دامنه
```

ویژگی‌ها:

- **فقط move** است، **کپی** نمی‌شود → مالکیت همیشه یکی است.
- اندازه‌اش به اندازهٔ یک اشاره‌گر خام است (بدون سربار اجرایی).
- `std::make_unique<T>(args...)` هم امن است و هم یک تخصیص دارد.

خروجی واقعی `01_unique_ptr.cpp`:

```
--- make_unique و دامنه ---
  + تخصیص: فایل
    استفاده از فایل
  اشاره‌گر خالی است؟ نه
  - آزادسازی: فایل
  بعد از خروج از دامنه
--- انتقال مالکیت با std::move ---
  + تخصیص: دیتابیس
  first خالی است؟ بله
    استفاده از دیتابیس
--- unique_ptr در vector ---
  + تخصیص: شبکه
  + تخصیص: کش
    استفاده از شبکه
    استفاده از کش
--- پایان دامنهٔ main ---
  - آزادسازی: شبکه
  - آزادسازی: کش
  - آزادسازی: دیتابیس
```

سه چیز که باید ببینید:

1. «آزادسازی: فایل» **قبل** از پیام بعدی چاپ شد — یعنی در پایان دامنه، بدون `delete`.
2. بعد از `std::move(first, second)`، `first` خالی است: مالکیت منتقل شد.
3. ترتیب آزادسازی در انتهای `main` برعکس ترتیب ساخت است (کش قبل از شبکه).

### چرا `unique_ptr` در `vector`؟

```cpp
std::vector<std::unique_ptr<Resource>> items;
items.push_back(std::make_unique<Resource>("شبکه"));
```

`vector` خودش نمی‌تواند اشیای غیرقابل‌کپی را با کپی مدیریت کند، ولی `unique_ptr` قابل انتقال است. نتیجه: مجموعه‌ای از اشیای چندریختی (`unique_ptr<Shape>`) بدون `new`/`delete` خام — همان چیزی که در جلسهٔ ۲۲ کم داشتیم.

## ۳. `shared_ptr` — مالکیت مشترک

```cpp
auto shared = std::make_shared<Node>("مشترک");
auto copy = shared;             // use_count = 2
```

شیء وقتی آزاد می‌شود که **آخرین** مالک برود. شمارش در بلوک کنترل ذخیره می‌شود، پس خود `shared_ptr` دو برابر یک اشاره‌گر خام است (اشاره‌گر + بلوک کنترل).

خروجی واقعی `02_shared_ptr.cpp`:

```
  + ساخت: مشترک
--- use_count ---
  بعد از ساخت: 1
  بعد از کپی: 2
    use_count داخل تابع: 2
  قبل از خروج از دامنه: 2
  بعد از خروج از دامنه: 1
  فقط یک مالک است؟ بله
--- reset ---
  - تخریب: مشترک
  بعد از reset: خالی
--- make_shared در برابر shared_ptr<T>(new T) ---
  + ساخت: یک تخصیص
  + ساخت: دو تخصیص
  هر دو کار می‌کنند، ولی make_shared یک تخصیص دارد.
  - تخریب: دو تخصیص
  - تخریب: یک تخصیص
```

نکته‌های مهم:

- `use_count` یک **عدد تقریبی** برای دیباگ است؛ در برنامهٔ چندنخی می‌تواند هم‌زمان تغییر کند. منطق برنامه را بر آن بنا نکنید.
- `reset()` مالکیت را رها می‌کند؛ اگر آخرین مالک بود، شیء تخریب می‌شود.
- `make_shared` یک تخصیص برای شیء و بلوک کنترل می‌دهد؛ نسخهٔ `shared_ptr<T>(new T)` دو تخصیص دارد و اگر تخصیص دوم شکست بخورد، خطر نشت دارد.

---

## ۴. `weak_ptr` — مشاهده بدون مالکیت

`shared_ptr` یک دام دارد: **چرخه**.

```cpp
first->friendShared = second;
second->friendShared = first;   // هر کدام use_count = 2
```

وقتی هر دو از دامنه خارج می‌شوند، `use_count` هر کدام ۲ است (یکی از متغیر محلی، یکی از شیء دیگر)، پس هیچ‌کدام صفر نمی‌شود و هیچ‌کدام آزاد نمی‌شود → **نشت حافظه**.

خروجی واقعی `03_weak_ptr_cycle.cpp`:

```
--- چرخه با shared_ptr (نشت) ---
  + ساخت: الف
  + ساخت: ب
  use_count الف: 2، ب: 2
  بعد از خروج از دامنه: هیچ «تخریب»ی چاپ نشد → حافظه نشت کرد
--- با weak_ptr (بدون نشت) ---
  + ساخت: ج
  + ساخت: د
  use_count ج: 1، د: 2
  weak با lock() قابل استفاده شد: ج
  weak expired است؟ نه
  - تخریب: ج
  - تخریب: د
  بعد از دامنه: هر دو تخریب شدند
--- weak به شیء آزادشده ---
  + ساخت: موقت
  داخل دامنه، expired: نه
  - تخریب: موقت
  بعد از دامنه، expired: بله
  lock() خالی است؟ بله
```

قواعد `weak_ptr`:

- `weak_ptr` مالک نیست و `use_count` را زیاد نمی‌کند.
- برای استفاده، `lock()` صدا بزنید که یک `shared_ptr` موقت می‌دهد؛ اگر شیء رفته باشد، خالی است.
- `expired()` بدون ساختن `shared_ptr` می‌پرسد «رفته است؟».
- `lock()` را در متغیر نگه دارید اگر چند بار استفاده می‌کنید؛ هر بار `lock()` دوباره چک می‌کند.

---

## ۵. کدام را انتخاب کنم

| نیاز | انتخاب |
|---|---|
| مالکیت انحصاری (پیش‌فرض) | `unique_ptr` |
| اشتراک واقعی مالکیت بین چند بخش | `shared_ptr` |
| اشاره بدون مالکیت (کش، ناظر، شکستن چرخه) | `weak_ptr` |
| فقط خواندن بدون مالکیت در امضای تابع | `T*` یا `const T&` |

قاعده: **از `unique_ptr` شروع کنید.** اگر بعداً معلوم شد مالکیت مشترک است، مهاجرت به `shared_ptr` آسان است؛ برعکسش سخت.

## ۷. اشتباهات رایج

1. **`auto p = std::make_unique<T>(); auto q = p;`** → خطای کامپایل، چون `unique_ptr` کپی نمی‌شود. `std::move` لازم است.
2. **استفاده از `p` بعد از `std::move(p)`** → `p` خالی است و `->` رفتار تعریف‌نشده دارد. بعد از انتقال بررسی کنید.
3. **`shared_ptr<T>(new T)` دو بار** → دو بلوک کنترل مستقل و **double free**:
   ```cpp
   T* raw = new T;
   std::shared_ptr<T> a(raw);
   std::shared_ptr<T> b(raw);   // ❌ فاجعه
   ```
4. **چرخهٔ `shared_ptr`** → نشت. یکی را `weak_ptr` کنید.
5. **`use_count` به‌عنوان منطق برنامه** → در چندنخی بی‌معنی است.
6. **`delete` روی اشاره‌گر `unique_ptr`** → دوباره آزادسازی. `delete` را کامل رها کنید.
7. **`std::shared_ptr<T>(this)`** → بلوک کنترل دوم. از `enable_shared_from_this` استفاده کنید.
8. **`weak_ptr` بدون `lock`** → دسترسی مستقیم ندارد.

## ۸. بهترین شیوه‌ها

- همیشه `make_unique`/`make_shared`؛ `new` را در کد روزمره ننویسید.
- امضای تابع را گویا کنید: `void take(std::unique_ptr<T>)` یعنی «مالکیت را می‌گیرم»، `void use(const T&)` یعنی «فقط نگاه می‌کنم».
- برای پارامتر فقط‌خواندنی `const T&` یا `T*` بگذارید، نه `shared_ptr` (که یک کپی و تغییر شمارنده هزینه دارد).
- چرخه‌های گراف (درخت والد/فرزند، گراف دوستانه) را با `weak_ptr` برای یال برگشتی بشکنید.
- `unique_ptr` با deleter سفارشی برای منابع غیرحافظه (فایل، سوکت) هم کار می‌کند — موضوع جلسهٔ ۳۸.

---

## ۹. خلاصه

- `unique_ptr` مالکیت انحصاری، فقط move، بدون سربار.
- `shared_ptr` مالکیت مشترک با شمارش مراجع و هزینهٔ بلوک کنترل.
- `weak_ptr` مشاهده بدون مالکیت؛ چرخه را می‌شکند و با `lock()` استفاده می‌شود.
- `make_unique`/`make_shared` را ترجیح دهید و `new`/`delete` خام را کنار بگذارید.

## ۱۱. قدم بعدی

جلسهٔ ۳۷ می‌رود سراغ موتور محرک این جلسه: **move semantics**. `std::move` دقیقاً چه می‌کند، سازندهٔ انتقال چگونه نوشته می‌شود، چرا `noexcept` مهم است و قانون پنج چیست.
