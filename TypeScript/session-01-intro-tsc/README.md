# جلسه ۱: چرا TypeScript؟ نصب، tsc، اولین برنامه، خواندن خطای کامپایلر (۱۲۰ دقیقه)

**محیط فرض:** Node.js LTS · TypeScript 5.x · از ریشهٔ `TypeScript/`: `npx tsc --noEmit` و `npx tsx`

## پیش‌نیازها
مسیر تقریبی [`js/`](../../js/) — حداقل ماژول، async، و کار با داده. این جلسه JavaScript را مرور نمی‌کند؛ فقط لایهٔ نوع را روی همان دانش سوار می‌کند.

اگر `node -v` و `npm -v` کار نمی‌کنند، اول [SETUP.md](../SETUP.md) را تمام کنید.

## اهداف قابل‌اندازه‌گیری
در پایان می‌توانید:

1. بگویید TypeScript چه چیزی به JavaScript **اضافه** می‌کند و چه چیزی را **عوض نمی‌کند**
2. تفاوت خطای **کامپایل** با خطای **runtime** را با یک مثال واقعی نشان دهید
3. یک فایل `.ts` بنویسید، با `npx tsx` اجرا کنید، و با `npx tsc --noEmit` نوع‌ها را چک کنید
4. یک پیام خطای `tsc` را تکه تکه بخوانید: فایل، خط، کد خطا (`TSxxxx`)، و معنی
5. بگویید چرا «کد اجرا شد پس نوع‌ها درست‌اند» استدلال خطرناکی است

## چرا مهم است؟
JavaScript تا لحظهٔ اجرا نمی‌فهمد که به جای عدد، `undefined` آمده. در پروژهٔ واقعی این یعنی باگ نیمه‌شب، نه خط قرمز در ادیتور.

TypeScript یک **لایهٔ ایستا** است: قبل از اجرا، قرارداد داده را چک می‌کند. کامپایلر دشمن شما نیست؛ همان هم‌تیمی است که قبل از کاربر، اشتباه را می‌بیند.

اگر این لایه را درست یاد بگیرید، ورود به React+TS (جلسه ۱۵) و خواندن کد دیگران چند برابر ارزان‌تر می‌شود. اگر غلط یاد بگیرید، `any` همه‌جا پخش می‌شود و انگار TypeScript ندارید.

## برنامه زمانی (۱۲۰ دقیقه)

| زمان | موضوع |
|------|--------|
| ۰–۱۵ | TypeScript چیست / چه نیست؛ رابطه با JS |

| ۱۰۰–۱۲۰ | تمرین + خودآزمایی |

## مفهوم عمیق

### ۱. TypeScript چیست؟

TypeScript = JavaScript + **سیستم نوع اختیاری که اجباری‌اش می‌کنیم** + ابزاری به نام کامپایلر (`tsc`).

سه واقعیت را همزمان در ذهن نگه دارید:

1. **هر برنامهٔ معتبر JS از نظر نحوی، TypeScript هم هست** — اما ممکن است از نظر نوع رد شود.
2. **نوع‌ها در runtime وجود ندارند.** مرورگر و Node فقط JavaScript می‌بینند. `string` و `number` روی متغیر، بعد از کامپایل پاک می‌شوند (type erasure).
3. **TypeScript زبان جداگانه‌ای با runtime خودش نیست.** مثل یک ویراستار سخت‌گیر روی همان JS است.

```ts
let age: number = 20;
// بعد از emit تقریباً می‌شود:
// let age = 20;
```

پس TypeScript «محافظ زمان نوشتن» است، نه «محافظ زمان اجرا». اگر داده از API خراب بیاید، مگر خودتان validate کنید، runtime همان JS است.

### ۲. چه چیزی نیست؟

- جایگزین React / Next / Vite نیست. آن‌ها را بعداً با TS مصرف می‌کنید.
- تست واحد نیست. `tsc` درست بودن نوع را چک می‌کند، نه درست بودن منطق کسب‌وکار.
- تضمین صفر باگ نیست. `as` و `any` و دادهٔ خارجی سوراخ می‌سازند.
- نسخهٔ «سخت‌تر JS» برای تنبیه مبتدی نیست. هدف: قرارداد واضح بین توابع و فایل‌ها.

### ۳. چرا اصلاً لایهٔ نوع؟

در JS این قانونی است و هیچ‌کس تا اجرا اعتراض نمی‌کند:

```js
function add(a, b) {
  return a + b;
}

add(1, 2);       // 3
add("1", 2);     // "12"  ← باگ خاموش
add(undefined, 1); // NaN
```

در TS با annotation:

```ts
function add(a: number, b: number): number {
  return a + b;
}

add(1, 2);     // ✅
// add("1", 2); // ❌ خطا قبل از اجرا
```

قرارداد «هر دو آرگومان عددند» از حدس به سند تبدیل شد. خوانندهٔ بعدی (همکار، خودِ شش‌ماه بعد) لازم نیست تابع را حدس بزند.

### ۴. کامپایلر چه کار می‌کند؟

دو شغل جدا:

| شغل | ابزار این دوره | خروجی |
|------|----------------|--------|
| چک نوع | `npx tsc --noEmit` | فقط خطا/موفقیت؛ فایل JS نمی‌سازد |
| اجرا برای دیدن رفتار | `npx tsx فایل.ts` | اجرای فوری بدون درگیر شدن با `outDir` |

در این دوره تقریباً همیشه `noEmit` کافی است: هدف یادگیری نوع است، نه ساخت bundle.

`tsx` TypeScript را در حافظه transpile می‌کند و با Node اجرا می‌کند. برای آموزش عالی است. در تولید، معمولاً `tsc` یا bundler (Vite) فایل را می‌سازد — جلسه ۱۳ و ۱۴.

### ۵. نقش `tsconfig.json`

فایل ریشهٔ [`../tsconfig.json`](../tsconfig.json) تصمیم‌های دوره را نگه می‌دارد:

- `strict: true` — سخت‌گیری پیش‌فرض حرفه‌ای (جلسه ۱۱ بازش می‌کند)
- `noEmit: true` — چک نوع بدون ساخت JS
- `module` / `moduleResolution`: `NodeNext` — هم‌خوان با Node مدرن (جلسه ۱۳)
- `include`: فقط `session-*/examples/**/*.ts`

تا جلسه ۱۳ این فایل را دستکاری نکنید مگر برای آزمایش آگاهانه. اگر تنظیمات را «چون خطا می‌داد» شل کنید، یادگیری خراب می‌شود.

### ۶. آناتومی یک خطای `tsc`

پیام نمونه:

```text
session-01-intro-tsc/examples/02-read-errors.ts:8:5 - error TS2322:
  Type 'string' is not assignable to type 'number'.
```

تکه‌ها:

1. **مسیر فایل** — کجا
2. **خط:ستون** (`8:5`) — کدام نویسه
3. **کد خطا** (`TS2322`) — خانوادهٔ مشکل؛ در مستندات قابل جست‌وجوست
4. **جملهٔ انگلیسی** — نوع سمت راست با نوع سمت چپ جور نیست

عادت درست: اول **نوع‌های دو طرف** را بخوانید، بعد کد را عوض کنید. عادت غلط: `as any` تا ساکت شود.

VS Code همان خطا را زیرخط قرمز می‌گذارد، چون زبان‌سرور از همان کامپایلر استفاده می‌کند. اگر ادیتور چیزی گفت و `tsc` چیز دیگری، معمولاً نسخهٔ TypeScript workspace فرق دارد — از ریشهٔ `TypeScript/` کار کنید.

### ۷. گردش کار پیشنهادی همین جلسه

از پوشهٔ `TypeScript/`:

```bash
npm install
npx tsc --noEmit
npx tsx session-01-intro-tsc/examples/01-hello.ts
```

ترتیب ذهنی:

1. بنویس
2. قرمز ادیتور را بخوان
3. `tsc --noEmit` برای تأیید کل دوره
4. `tsx` فقط وقتی منطق runtime را می‌خواهی ببینی

### ۸. چیزی که عمداً اینجا درس نمی‌دهیم

جنریک، `interface` در برابر `type`، `tsconfig` پیشرفته، React — هر کدام جلسهٔ خودشان را دارند. این جلسه فقط باید حس «کامپایلر حرف می‌زند و من می‌فهمم» را بسازد.

## اشتباه‌های رایج

1. **فکر کردن که TypeScript در مرورگر/Node اجرا می‌شود.** اجرا همیشه JS است. نوع‌ها پاک می‌شوند.
2. **نادیده گرفتن خطا چون `tsx` هنوز اجرا کرد.** بعضی ابزارها transpile می‌کنند حتی با خطای نوع. اجرا ≠ سلامت نوع.
3. **خاموش کردن خطا با `any` یا `// @ts-ignore` از جلسهٔ اول.** بدهی فنی از روز صفر.
4. **نصب جهانی گیج‌کننده (`npm i -g typescript`) و نسخهٔ متفاوت با پروژه.** این دوره با `npx` از `node_modules` محلی کار می‌کند.
5. **خواندن فقط خط اول خطا و حدس زدن.** کد `TSxxxx` و دو نوع دو طرف را بخوانید.

## الگوی بهتر

- یک `tsconfig` در ریشه؛ مثال‌ها داخل `include`
- چک نوع با `tsc --noEmit`؛ اجرا با `tsx` وقتی لازم است
- خطا را با **درست کردن قرارداد نوع** ببندید، نه با دور زدن کامپایلر
- نسخهٔ TypeScript را از `package.json` همین پوشه بگیرید، نه از حافظه

## تمرین‌ها

### آسان
در یک فایل جدید (مثلاً `examples/practice-easy.ts`) تابع `greet(name: string): string` بنویسید که `سلام، {name}` برگرداند. یک بار با رشته صدا بزنید. یک بار عمداً عدد بدهید، خطا را بخوانید، بعد صدا را درست کنید.

### چالشی
تابعی به نام `double` بنویسید که فقط `number` بگیرد و دو برابرش را برگرداند. سه فراخوانی در ذهن/کامنت بنویسید: درست، اشتباه نوع، و موردی که **از نظر نوع قبول است ولی از نظر منطق غلط** (مثلاً `double(NaN)`). توضیح دهید چرا `tsc` مورد سوم را رد نمی‌کند.

## راهنمای حل

آسان: `function greet(name: string): string { return \`سلام، ${name}\`; }` — آرگومان عدد `TS2345` می‌دهد.

چالش: `function double(n: number): number { return n * 2; }` — `NaN` در JavaScript از نوع number است؛ TypeScript همان مدل را دارد. نوع ≠ اعتبارسنجی دامنه. اگر باید عدد متناهی باشد، خودتان `Number.isFinite` بگذارید (منطق)، نه اینکه از کامپایلر معجزه بخواهید.

## خودآزمایی

1. TypeScript در runtime چه می‌شود؟
2. تفاوت `tsc --noEmit` و `tsx` چیست؟
3. چرا «اجرا شد پس نوع‌ها درست‌اند» غلط است؟
4. چهار بخش یک پیام خطای `tsc` کدام‌اند؟
5. `tsconfig.json` این دوره را چرا نباید همین جلسه شل کرد؟
6. `any` از جلسهٔ اول چه آسیبی می‌زند؟
7. آیا هر فایل JS از نظر نحوی TS است؟ از نظر نوع چطور؟
8. type erasure یعنی چه؟
9. اگر ادیتور خطا داد ولی شما `npx tsc` را از پوشهٔ دیگری زدید، چه باید چک کنید؟
10. این دوره جایگزین کدام مسیر است و جایگزین کدام نیست؟ (`js/` در برابر ساخت اپ React)

## جمع‌بندی و پل جلسهٔ بعد
الان می‌دانید TypeScript لایهٔ نوع روی JS است، کامپایلر قبل از اجرا حرف می‌زند، و پیام خطا خواندنی است. جلسهٔ بعد: کی نوع را **بنویسید** و کی بگذارید کامپایلر **حدس بزند**؛ primitiveها؛ و چرا `any` نباید عادت شود.
