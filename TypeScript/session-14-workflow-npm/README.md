# جلسه ۱۴: گردش کار tsc و npm — خطا، اسکریپت، CI محلی، دام tsx (۱۲۰ دقیقه)

**محیط فرض:** [`package.json`](../package.json) · از ریشهٔ `TypeScript/`

## پیش‌نیازها
جلسات ۱ و ۱۳ · آشنایی با npm.

## اهداف قابل‌اندازه‌گیری
در پایان می‌توانید:

1. `npm run typecheck` را به‌عنوان عادت قبل از «تمام شد» اجرا کنید
2. خطای چندخطی `tsc` را تکه تکه بخوانید (فایل، خط، کد، Related)
3. در یک جمله فرق `tsc` و `tsx` را بگویید و دام «اجرا شد پس نوع درست است» را رد کنید
4. اسکلت اسکریپت npm برای پروژهٔ شخصی‌تان طراحی کنید
5. بگویید CI محلی یعنی چه (typecheck قبل از push)

## چرا مهم است؟
در PR واقعی معمولاً typecheck اجباری است. اگر فقط `tsx` عادت شما باشد، سر CI غافلگیر می‌شوید — چون بعضی ابزارها با وجود خطای نوع اجرا می‌کنند.

## مفهوم عمیق

### ۱. اسکریپت‌های این دوره

```json
"scripts": {
  "typecheck": "tsc --noEmit",
  "run:example": "tsx"
}
```

`npm run typecheck` همان قرارداد تیمی است؛ مسیر `tsc` از `node_modules` می‌آید.

### ۲. خواندن خطا

```text
file.ts:10:5 - error TS2322: Type 'string' is not assignable to type 'number'.
```

ترتیب ذهنی: کجا → کدام نوع‌ها → چرا ناسازگار → اصلاح قرارداد (نه any).

گاهی چند خط Related information مسیر inference را نشان می‌دهد — آن‌ها را نادیده نگیرید.

### ۳. دام tsx

`tsx` برای یادگیری عالیست. اما:

- ممکن است فایلی با خطای نوع را همچنان اجرا کند (بسته به شرایط)
- جایگزین typecheck در CI نیست

قانون: **سبز بودن runtime ≠ سبز بودن نوع**.

### ۴. گردش کار پیشنهادی

1. بنویس  
2. قرمز ادیتور را بخوان  
3. `npm run typecheck`  
4. در صورت نیاز `npx tsx مسیر` برای رفتار  
5. قبل از push دوباره typecheck  

### ۵. CI محلی

حتی بدون GitHub Actions، همان دستور CI را محلی عادت کنید. سورپرایز کمتر.

### ۶. @ts-expect-error

اگر لازم شد، یک خط توضیح چرا. صدها expect-error بدون توضیح = بوی مرگ.

### ۷. node_modules

نصب محلی؛ commit نکنید. قفل وابستگی را با lockfile پروژه بفهمید.

### ۸. گسترش بعدی

ESLint + typescript-eslint جلسه ۳۷؛ اینجا تمرکز tsc است.

---

## اشتباه‌های رایج

1. **فقط runtime و نادیده typecheck.** علت: دام tsx.
2. **any برای سبز کردن CI.** علت: بدهی.
3. **commit node_modules.** علت: حجم و تضاد ماشین‌ها.
4. **خواندن فقط خط اول خطا.** علت: Related مهم است.
5. **تغییر اسکریپت ریشه دوره بدون هماهنگی.** علت: بقیه روی `typecheck` حساب می‌کنند.

## الگوی بهتر

قبل از «تمام»: typecheck. خطا را با قرارداد درست ببندید. tsx را برای دیدن رفتار نگه دارید نه برای اثبات نوع.

## تمرین‌ها

### آسان
`npm run typecheck` را اجرا و خروجی موفق را تأیید کنید.

### چالشی
موقتاً در یک فایل کپی شخصی نوعی را خراب کنید، پیام را بلند بخوانید، درست کنید؛ به ریپو commit خراب نکنید.

## راهنمای حل

پیام `is not assignable` → نوع چپ و راست را هم‌تراز کنید.

## خودآزمایی

1. اسکریپت npm کجا تعریف می‌شود؟
2. tsc با tsx چه فرقی دارد؟
3. چرا node_modules در git نیست؟
4. چهار بخش پیام خطا؟
5. CI چرا typecheck می‌خواهد؟
6. دام «اجرا شد پس نوع درست» چیست؟
7. Related information چیست؟
8. @ts-expect-error کی مجاز است؟
9. ترتیب گردش کار پیشنهادی؟
10. آیا tsx جایگزین CI است؟
