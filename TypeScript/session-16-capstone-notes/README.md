# جلسه ۱۶: Capstone میانی — ماژول Note تایپ‌شده (۱۲۰ دقیقه)

**محیط فرض:** TypeScript 5.x · `npx tsc --noEmit` · `npx tsx` · بدون UI فریم‌ورک

## پیش‌نیازها
جلسات ۸–۱۲ و ۱۴. این جلسه جمع‌بندی مسیر پایه است (شبیه پروژه میانی مسیر Py)، نه پایان کل دورهٔ ۵۰جلسه‌ای.

## اهداف قابل‌اندازه‌گیری
در پایان می‌توانید:

1. مدل `Note` و عملیات خالص `add` / `toggle` / `remove` / `filterOpen` را تایپ کنید
2. ماژول‌ها را جدا نگه دارید (`types` / `notes` / `main`)
3. با `import type` و آرایهٔ immutable کار کنید
4. کل مسیر را با `tsc --noEmit` سبز کنید
5. بگویید قدم بعدی پایه React است و جلسات ۱۷+ سیستم نوع پیشرفته‌اند

## چرا مهم است؟
تا اینجا ابزارها جدا بودند. اینجا باید **یک برش عمودی** بسازید: مدل + قوانین دامنه + ورودی برنامه — همان چیزی که بعداً UI صدا می‌زند.

## مفهوم عمیق

### ۱. منبع حقیقت

```ts
export type Note = { id: string; text: string; done: boolean };
```

UI بعدی فقط همین را می‌شناسد. فیلد اضافه را اینجا تصمیم بگیرید نه در سه جا.

### ۲. خلوص و immability

```ts
export function toggleNote(notes: Note[], id: string): Note[] {
  return notes.map((note) =>
    note.id === id ? { ...note, done: !note.done } : note,
  );
}
```

آرایهٔ ورودی را mutate نکنید. تست‌پذیری و پیش‌بینی بالا می‌رود.

### ۳. جداسازی فایل

- `types.ts` — فقط نوع  
- `notes.ts` — منطق  
- `main.ts` — سیم‌کشی دمو  

بعداً `app/` می‌تواند main را عوض کند بدون دست زدن به دامنه.

### ۴. create و اعتبار متن

`trim` و رد کردن متن خالی — منطق دامنه، نه کار کامپایلر.

### ۵. import type

```ts
import type { Note } from "./types.js";
```

نوع را از مقدار جدا نگه دارید (جلسه ۱۰).

### ۶. tsc به‌عنوان تست ذهنی

اگر امضای `toggleNote` بشکند، مصرف‌کننده‌ها قرمز می‌شوند. برای این سطح، typecheck همان تور ایمنی است.

### ۷. گسترش آگاهانه

`filterOpen` نمونهٔ query روی مجموعه است. فیلترهای بعدی (`filterDone`) همان الگو.

### ۸. پل به ۱۷+ و ۵۰

جلسه ۱۷ به بعد سیستم نوع عمیق‌تر است. جلسه ۵۰ capstone نهایی بزرگ‌تر (سرویس چندلایه) خواهد بود. ۱۶ را تمام‌شدهٔ پایه بدانید نه تمام علم TS.

## اشتباه‌های رایج

1. **mutate آرایهٔ ورودی.** علت: اثر جانبی پنهان.
2. **id از نوع any یا number تصادفی بدون قرارداد.** علت: کلید ناپایدار.
3. **قاطی parse UI با منطق دامنه در یک فایل.** علت: تست سخت.
4. **کپی Note در سه فایل.** علت: انحراف نوع.
5. **نادیده typecheck چون main چاپ می‌کند.** علت: دام runtime.

دامنه خالص و typed؛ UI فقط صدا می‌زند؛ typecheck سبز قبل از ادعا «تمام».

## تمرین‌ها

### آسان
یک note اضافه و چاپ کنید.

### چالشی
`filterDone(notes)` و در سناریو استفاده کنید؛ یا `renameNote(notes, id, text)`.

## راهنمای حل

آسان: `addNote` در main.

چالش: `notes.filter((n) => n.done)` یا map با تغییر text روی id.

## خودآزمایی

1. چرا آرایهٔ جدید برمی‌گردانیم؟
2. جداسازی types چه کمکی می‌کند؟
3. چطور کل دورهٔ پایه را typecheck کنیم؟
4. قدم React چیست؟
5. آیا React-project را تغییر دهیم؟
6. import type چرا؟
7. trim خالی چه کسی مسئول است؟
8. فرق جلسه ۱۶ و ۵۰ چیست؟
9. id را از کجا می‌سازیم؟
10. mutate چرا بد است؟

## جمع‌بندی و پل جلسهٔ بعد
برش عمودی Note را تایپ‌شده بستید. جلسهٔ ۱۷: **discriminated unions** عمیق‌تر — همان الگویی که در Result و state ماشین‌ها حرفه‌ای می‌شود.
