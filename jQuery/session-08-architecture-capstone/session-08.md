# جلسه ۸ — معماری، الگوهای طراحی و پروژه نهایی (Capstone)

## بخش اول: چرا معماری در یک پروژه jQuery مهم است؟

وقتی یک پروژه jQuery بزرگ می‌شود (چند هزار خط)، اگر همه‌چیز در یک فایل و بدون ساختار نوشته شود، مشکلات زیر پیش می‌آید:

- تداخل نام متغیرها و توابع (Global Namespace Pollution)
- سختی پیدا کردن اینکه کدام قطعه کد مسئول کدام رفتار است
- وابستگی شدید بین بخش‌های مختلف (تغییر یک بخش، بخش‌های دیگر را می‌شکند)

راه‌حل: استفاده از الگوهای طراحی ساده که در ادامه می‌بینیم.

## بخش دوم: Module Pattern (الگوی ماژول)

### ۲.۱ ایده اصلی

به‌جای نوشتن توابع و متغیرها مستقیم در `window` (سراسری)، همه‌چیز را داخل یک IIFE (تابعی که بلافاصله اجرا می‌شود) قرار می‌دهیم و فقط چیزهایی را که لازم است از بیرون قابل‌دسترس باشند، آشکار (expose) می‌کنیم:

```javascript
var GalleryModule = (function ($) {
  'use strict';

  // ---- متغیرهای خصوصی (فقط داخل این ماژول قابل‌دسترس‌اند) ----
  var images = [];
  var currentFilter = 'all';

  // ---- توابع خصوصی ----
  function render() {
    var $grid = $('#galleryGrid');
    $grid.empty();
    $.each(images, function (i, img) {
      if (currentFilter !== 'all' && img.category !== currentFilter) return;
      $grid.append('<div class="gallery-item">' + img.title + '</div>');
    });
  }

  // ---- API عمومی (چیزی که بیرون از ماژول قابل استفاده است) ----
  return {
    init: function (initialImages) {
      images = initialImages;
      render();
    },
    setFilter: function (category) {
      currentFilter = category;
      render();
    },
    addImage: function (img) {
      images.push(img);
      render();
    }
  };

})(jQuery);

// استفاده از بیرون:
GalleryModule.init([{ title: 'عکس ۱', category: 'nature' }]);
GalleryModule.setFilter('nature');
```

مزیت اصلی: `images` و `render` از بیرون این IIFE اصلاً قابل‌دسترس یا تغییر مستقیم نیستند — فقط از طریق متدهایی که خودِ ماژول تعریف کرده (`init`, `setFilter`, `addImage`) می‌توان با آن کار کرد. این یعنی **Encapsulation** واقعی، حتی بدون کلاس‌های ES6.

### ۲.۲ چند ماژول مستقل که با هم کار می‌کنند

در یک پروژه واقعی معمولاً چند ماژول دارید (`GalleryModule`, `FilterModule`, `SearchModule`, ...) که باید با هم ارتباط داشته باشند، بدون اینکه مستقیماً به هم وابسته باشند. اینجا الگوی بعدی به کمک می‌آید:

## بخش سوم: Event Bus / Pub-Sub Pattern (الگوی ناشر-مشترک)

### ۳.۱ مشکل: وابستگی مستقیم بین ماژول‌ها

```javascript
// ❌ بد: SearchModule مستقیماً GalleryModule را صدا می‌زند
// یعنی این دو ماژول به‌شدت به هم وابسته‌اند (Tight Coupling)
SearchModule.onSearch = function (term) {
  GalleryModule.filterByTerm(term); // وابستگی مستقیم!
};
```

### ۳.۲ راه‌حل: استفاده از خودِ jQuery به‌عنوان Event Bus

نکته جالب: چون `$(document)` (یا هر المان دیگر) می‌تواند رویداد سفارشی `trigger` و `on` کند، می‌توانیم از آن به‌عنوان یک "میانجی پیام‌رسانی" بین ماژول‌ها استفاده کنیم، بدون اینکه ماژول‌ها مستقیم همدیگر را بشناسند:

```javascript
// SearchModule فقط یک رویداد "پرتاب" می‌کند، اصلاً نمی‌داند چه کسی گوش می‌دهد:
var SearchModule = (function ($) {
  function onSearchInput(term) {
    $(document).trigger('search:changed', [term]); // پرتاب رویداد سفارشی
  }
  return {
    init: function () {
      $('#searchBox').on('input', function () {
        onSearchInput($(this).val());
      });
    }
  };
})(jQuery);

// GalleryModule فقط گوش می‌دهد، اصلاً نمی‌داند این رویداد از کجا آمده:
var GalleryModule = (function ($) {
  function filterByTerm(term) { /* ... */ }
  return {
    init: function () {
      $(document).on('search:changed', function (event, term) {
        filterByTerm(term);
      });
    }
  };
})(jQuery);

// راه‌اندازی برنامه:
$(document).ready(function () {
  SearchModule.init();
  GalleryModule.init();
});
```

این الگو **Loose Coupling** ایجاد می‌کند: می‌توانید `SearchModule` را کاملاً حذف یا جایگزین کنید، بدون اینکه `GalleryModule` بشکند (چون فقط منتظر یک رویداد نام‌گذاری‌شده است، نه یک ماژول خاص).

### ۳.۳ قرارداد نام‌گذاری رویدادهای سفارشی

برای رویدادهای سفارشی برنامه، قراردادی مثل `namespace:action` رایج است (`search:changed`, `cart:itemAdded`, `modal:closed`) تا از تداخل با رویدادهای بومی مرورگر (`click`, `change`) جلوگیری شود و خواندن کد ساده‌تر باشد.

## بخش چهارم: مروری بر مهاجرت به دنیای مدرن

اگر روزی پروژه بزرگ شود و بخواهید از jQuery به یک فریم‌ورک مدرن (React/Vue) مهاجرت کنید، نکات زیر کمک می‌کند:

1. **جدا نگه‌داشتن منطق (Logic) از دستکاری DOM** از همین امروز (همان‌طور که در Module Pattern دیدیم) مهاجرت را بسیار ساده‌تر می‌کند، چون منطق تجاری (قوانین فیلتر، اعتبارسنجی) را می‌توانید تقریباً بدون تغییر به یک کامپوننت React منتقل کنید.
2. **Event Bus Pattern شبیه به State Management** (مثل Redux/Vuex) است — یادگیری این الگو در jQuery، درک مفاهیم فریم‌ورک‌های مدرن را آسان‌تر می‌کند.
3. مهاجرت معمولاً **تدریجی** (Incremental) انجام می‌شود: صفحه‌به‌صفحه یا کامپوننت‌به‌کامپوننت، نه یک‌باره کل پروژه.

## بخش پنجم: پروژه نهایی (Capstone) — داشبورد گالری تصاویر

فایل `code/index.html` این جلسه یک پروژه کامل و ترکیبی از همه ۸ جلسه دوره است:

### ویژگی‌ها

- نمایش گالری تصاویر (placeholder رنگی به‌جای تصویر واقعی، برای اجرای آفلاین)
- **جستجوی زنده** با debounce (جلسه ۴ و ۷)
- **فیلتر بر اساس دسته‌بندی** با دکمه‌های Tab-مانند (جلسه ۶)
- **Drag & Drop برای تغییر ترتیب** تصاویر (جلسه ۶)
- **افزودن تصویر جدید** با فرم دارای اعتبارسنجی ساده (جلسه ۷)
- **ذخیره خودکار ترتیب و لیست در `localStorage`** (جلسه ۷) — با رفرش صفحه، تغییرات از دست نمی‌روند
- **معماری Module Pattern + Event Bus**: کد به سه ماژول مستقل تقسیم شده: `GalleryModule` (رندر و مدیریت داده)، `FilterModule` (دکمه‌های فیلتر)، `SearchModule` (جستجو) — که فقط از طریق رویدادهای سفارشی روی `document` با هم حرف می‌زنند.
- **پلاگین کوچک `toastNotify`** برای بازخورد کاربر (از جلسه ۴، بازنویسی‌شده)

### ساختار کد (خلاصه معماری)

```
AppEventBus (خودِ $(document)) 
     ▲                    ▲
     |                    |
SearchModule          FilterModule
     |                    |
     └──────► trigger('gallery:filterChanged') ─────┐
                                                      ▼
                                              GalleryModule
                                          (تنها جایی که DOM گالری را رندر می‌کند)
                                                      │
                                                      ▼
                                              localStorage (ماندگاری داده)
```

هر ماژول فقط مسئول یک کار است (Single Responsibility) و فقط با رویداد با بقیه حرف می‌زند — این دقیقاً همان معماری‌ای است که در پروژه‌های بزرگ jQuery (و حتی الهام‌گرفته از آن در فریم‌ورک‌های مدرن) استفاده می‌شود.

## ۶. تله‌های رایج معماری

1. **نوشتن همه‌چیز در `$(document).ready` یک فایل بزرگ** بدون تفکیک به ماژول → نگهداری غیرممکن می‌شود بعد از چند صد خط.
2. **وابستگی مستقیم بین توابع دو بخش مختلف برنامه** (Tight Coupling) → تغییر یک بخش بقیه را می‌شکند.
3. **استفاده از رویداد سفارشی بدون قرارداد نام‌گذاری مشخص** → تداخل احتمالی با رویدادهای بومی یا رویدادهای پلاگین‌های دیگر.
4. **فراموش‌کردن ذخیره state در localStorage بعد از هر تغییر** (مثلاً فقط بعد از افزودن ولی نه بعد از Drag & Drop) → ناهماهنگی بین آنچه کاربر می‌بیند و آنچه ذخیره شده.

## ۷. تمرین‌های پیشنهادی نهایی

1. یک ماژول جدید `StatsModule` اضافه کنید که با گوش‌دادن به رویدادهای `gallery:imageAdded` و `gallery:imageRemoved`، تعداد کل تصاویر را در گوشه صفحه نمایش دهد — بدون اینکه مستقیماً `GalleryModule` را صدا بزند.
2. قابلیت «حذف تصویر» را با دکمه‌ای روی هر آیتم گالری اضافه کنید (با Event Delegation و به‌روزرسانی localStorage).
3. یک Dark Mode Toggle بسازید که وضعیتش هم در localStorage ذخیره شود و با بارگذاری مجدد صفحه حفظ شود.
4. با `console.time()` سرعت رندر گالری با ۵۰۰ آیتم را در دو حالت مقایسه کنید: append در حلقه در برابر ساخت رشته HTML و append یکجا (یادآوری جلسه ۴).
