# جلسه ۱۴: دیباگ Compose (۹۰ دقیقه)

**محیط فرض:** Docker Desktop / Engine · [SETUP.md](../SETUP.md)

## پیش‌نیازها
جلسات ۱۱–۱۳.

## اهداف قابل‌اندازه‌گیری
1. با `docker compose logs -f` مشکل را پیدا کنید
2. با `docker compose exec` داخل سرویس بروید
3. پورت گیرکرده را تشخیص و سرویس را down کنید
4. تفاوت `restart` بی‌پایان با خواندن لاگ خطا را بگویید

## چرا مهم است؟
بیشتر زمان واقعی صرف دیباگ است نه نوشتن YAML اول.

## مفهوم عمیق
چک‌لیست سریع:
1. `compose ps` — وضعیت و پورت
2. `compose logs SERVICE` — خطا
3. `compose exec SERVICE sh` — فایل/شبکه داخل
4. از میزبان: آیا پورت publish شده؟ از کانتینر دیگر: آیا نام DNS درست است؟

## اشتباه‌های رایج
1. فقط restart پشت‌سرهم بدون خواندن لاگ.
2. دیباگ با `localhost` داخل شبکهٔ اشتباه.
3. کشتن پروسهٔ میزبان به‌جای `compose down`.

## مثال گام‌به‌گام
```powershell
powershell -File Docker/session-14-compose-debug/examples/01-debug-flow.ps1
```

## الگوی بهتر
یک تغییر، یک فرضیه، یک مشاهده (لاگ/exec)؛ نه سه تغییر همزمان.

## تمرین‌ها
### آسان
عمداً پورت را به مقدار اشغال‌شده بگذارید و پیام خطا را بخوانید.
### چالشی
یک typo در نام سرویس proxy بگذارید و از لاگ nginx علت را بیابید.

## راهنمای حل
اسکریپت استک سالم را بالا می‌آورد و دستورات دیباگ نمونه را چاپ/اجرا می‌کند.

## خودآزمایی
1. اولین دستور دیباگ؟
2. `exec` چه وقت شکست می‌خورد؟
3. پورت اشغال را چطور آزاد کنید؟
4. چرا restartalone کافی نیست؟
5. `logs --tail` چه کمکی می‌کند؟
